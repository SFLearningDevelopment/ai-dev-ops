Step 1 of 5
The problem

The CI/CD pipeline from Example 5 has been running in production for six months. When it was introduced, it completed in approximately 8 minutes. It now regularly takes 22–26 minutes. No single change caused this — it is the accumulated result of six months of normal engineering activity: dependency updates, new test files, workflow additions, and caching configuration that was correct at the start but has not kept pace with the project's growth.

This is the Tier 3 scenario where the failure mode is gradual degradation rather than a discrete incident. There is no PagerDuty alert, no error log, no obvious signal. The pipeline still passes. It is simply getting slower in a way that is costing the team 15–18 minutes of developer wait time per PR — which at 40 PRs per week is roughly 10 hours of accumulated idle time per week.

What makes gradual degradation harder to diagnose
A discrete incident has a timestamp — "it broke at 14:00." Gradual degradation has a trend — "it has been getting slower since September." Sequential investigation of a single run's job log will not reveal a trend. The triage requires reading job timing data across multiple runs, correlating it with dependency growth and cache configuration, and identifying which specific changes in a six-month window contributed the most to the slowdown.

The naive approach

The naive approach to a slow pipeline is to look at the most recent run's job log and identify the longest step. This finds the current bottleneck — but not why it became a bottleneck, or whether there are multiple contributing factors that together produce the degradation.

The naive investigation
Engineer opens the most recent failed run log → identifies npm ci as the longest step at 11 minutes → adds a comment to the PR: "npm install is slow, maybe we need to update our node version" → closes the tab. Next PR is equally slow. The real causes — cache invalidation due to lock file churn, a 3x dependency count increase, a sequential job structure that was efficient at 8 minutes but is wasteful at 24, and a Trivy scan that rescans the same base image layers every run — are not visible from a single run log.
  • Methodology
    Single-run analysis finds the current symptom, not the trend's causes. Looking at one job log identifies that npm ci takes 11 minutes today. It does not reveal that 4 months ago it took 3 minutes, that the growth correlates with three major dependency updates, or that the cache is now missing 78% of the time because the lock file is modified on nearly every PR.
  • Methodology
    Sequential job structure was an acceptable tradeoff at 8 minutes, not at 24. The original pipeline design ran test, scan, and some setup steps sequentially because the total time was short enough that parallelisation overhead was not worthwhile. At 24 minutes, the sequential design is the primary structural bottleneck — but this is only visible when job timing history shows which jobs grew and which stayed flat.

What is causing the slowdown and in what order should I fix it?

Claude Code

Three distinct causes, each with a clear signal in the evidence. In descending order of impact:

Cause 1 — Cache hit rate collapse (November) is the primary driver. The cache hit rate dropped from 82% to 31% in the week of November 1st — correlating exactly with the cache-dependency-path change from package-lock.json to **/package-lock.json. The glob pattern matches any package-lock.json anywhere in the repo, including in node_modules subdirectories that change on every install. This means the cache key is computed from a lockfile that mutates during the install itself — invalidating the cache on the next run. With 19% hit rate today, the team is running full npm ci from scratch on 81% of runs. At 847 packages and 2.4 MB of lock data, a cold install takes 10–12 minutes.

Cause 2 — max-parallel: 1 serialises the matrix (October). Setting max-parallel: 1 was intended to reduce runner costs. The effect is that Node 18 tests run first (11 minutes), then Node 20 tests run (11 minutes) — 22 minutes total for the test stage alone. Before this change, both ran in parallel — 11 minutes total. This change doubled the test stage wall time. The job timing table shows test-18x and test-20x both growing in lockstep, which confirms they are running sequentially rather than in parallel.

Cause 3 — Trivy rescans the full image including unchanged base layers. The scan job duration grew from 1.8 minutes to 5.2 minutes. The scan-type: 'image' setting causes Trivy to download and scan all layers including the base Node.js image on every run, even when only application code changed. Switching to filesystem scan on the application layer alone — or using Trivy's layer caching — reduces scan time by 60–70% for runs where the base image has not changed.

The dependency growth is a contributing factor but not a primary cause. Dependency count grew 2.7x (312 → 847 packages). Without the cache regression, this growth would have increased cold install time proportionally — but with a 89% cache hit rate, it would affect only 11% of runs. The dependency growth only became a pipeline problem when the cache stopped working. Fixing the cache key recovers the majority of the lost time independently of dependency count.

Show me the exact YAML changes to remove max-parallel: 1 and restore parallel matrix execution. Also — if we are running two parallel runners anyway, is there any way to share the npm install between the two matrix jobs instead of running it twice?

Claude Code

Fix 1: Remove max-parallel: 1 — one line deletion:

.github/workflows/cicd.yml — restore parallel matrix
test:
  strategy:
    matrix:
      node-version: ['18.x', '20.x']
    # Remove: max-parallel: 1
    fail-fast: false   # Both versions complete even if one fails

On sharing npm install between matrix jobs: GitHub Actions does not support sharing a working directory between jobs — each job runs on a fresh runner with a clean filesystem. The only sharing mechanism is the cache. With a correctly keyed cache, each matrix job will hit the cache independently and restore in ~45 seconds rather than running a full install. This is the correct model — the cache key fix from Turn 4 is what makes parallel matrix efficient.

There is a pattern where a setup job runs install once and uploads node_modules as an artifact for the matrix jobs to download. This works but is generally slower than a cache hit — artifact upload/download has more overhead than cache restore for large node_modules directories. With a working cache, the standard pattern is better. Do not add a setup job — fix the cache key first.

Turn 4 of 5 — Cache key fix
Engineer → Claude Code

Show the exact cache key fix. Also explain why the glob pattern causes the cache to invalidate — I want to understand this well enough to explain it to the team.

Claude Code
.github/workflows/cicd.yml — cache key fix
- uses: actions/setup-node@v4
  with:
    node-version: ${{ matrix.node-version }}
    cache: 'npm'
    # Before (broken): '**/package-lock.json'
    # After (correct):  'package-lock.json'
    cache-dependency-path: 'package-lock.json'

Why the glob caused the problem — for the team explanation:

GitHub Actions computes the npm cache key by hashing the file(s) matched by cache-dependency-path. The key is something like node-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}.

**/package-lock.json matches every package-lock.json file in the entire repository tree — including the ones inside node_modules/ subdirectories that have their own nested lock files. When npm ci runs, it modifies files inside node_modules/. On the next run, the glob matches the modified files inside node_modules/, computes a different hash, gets a cache miss, runs npm ci again, modifies the files again — the cycle repeats on every run.

package-lock.json (no glob) matches only the single lock file in the project root. This file changes only when dependencies are explicitly updated — which is the correct cache invalidation condition. Cache hit rate should recover to 85–90%+ within a week of this change.

Turn 5 of 5 — Trivy scan optimisation
Engineer → Claude Code

Show the Trivy scan changes to avoid rescanning unchanged base layers. We still need to scan the full image for the first run after a base image update, but for all other runs we only need to scan the application layer changes.

Claude Code

Two changes: switch from image scan to filesystem scan for the application layer, and add a separate scheduled job that scans the full image weekly for base layer vulnerabilities.

.github/workflows/cicd.yml — Trivy scan optimisation
  scan:
    needs: test
    steps:
      - uses: actions/checkout@v4

      # Build app layer only (not push) — reuses GHA cache
      - name: Build image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: false
          load: true
          tags: payment-api:scan
          cache-from: type=gha

      # Extract application filesystem from image for scanning
      - name: Export app filesystem
        run: |
          docker create --name scan-container payment-api:scan
          docker cp scan-container:/app ./app-fs
          docker rm scan-container

      # Scan only the application layer — not base OS packages
      - name: Scan application layer
        uses: aquasecurity/trivy-action@0.28.0
        with:
          scan-type: 'fs'        # Filesystem scan — no base layer download
          scan-ref: './app-fs'  # Only scan extracted app directory
          trivy-config: .trivy.yaml
          output: trivy-report.json

      - name: Upload scan report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: trivy-report-${{ github.sha }}
          path: trivy-report.json
          retention-days: 30
.github/workflows/base-image-scan.yml — weekly full image scan
name: Weekly base image vulnerability scan
on:
  schedule:
    - cron: '0 6 * * 1'   # Every Monday at 06:00 UTC
  workflow_dispatch:    # Also triggerable manually

jobs:
  full-image-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build full image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: false
          load: true
          tags: payment-api:weekly-scan
      - name: Full image scan including base layers
        uses: aquasecurity/trivy-action@0.28.0
        with:
          scan-type: 'image'
          image-ref: payment-api:weekly-scan
          trivy-config: .trivy.yaml
          output: trivy-base-report.json

The tradeoff: PR scans now cover only application-layer vulnerabilities (npm packages, application code). Base OS package vulnerabilities are covered by the weekly scan. For a payment service, this is an acceptable split — base image CVEs are typically discovered on a weekly cycle by security teams, not on a per-PR cycle. If your security policy requires full image scanning on every PR, keep scan-type: 'image' and accept the 5-minute scan time.

Step 5 of 5
Watch out

Claude Code correctly identified three independent causes of the degradation from simultaneous evidence, ranked them by impact, and produced targeted fixes. Here is what requires verification in your specific pipeline and security context.

What Claude Code handled well
Cache hit rate collapse traced to the glob pattern change in the exact week it appeared in the evidence, max-parallel: 1 identified as the serialisation cause from the job timing table, impact arithmetic correct (both test jobs equal duration, sequential → twice the wall time), dependency growth correctly framed as contributing context rather than a primary cause, correct rejection of the "shared install via artifact" pattern in favour of cache-based sharing, Trivy scan tradeoff articulated honestly (PR scan covers app layer; base OS requires weekly job or accept longer PR scan time).
  • Verify
    The cache hit rate projections assume the root lockfile changes infrequently. The projection of 87%+ cache hit rate assumes package-lock.json in the project root changes on roughly 10–15% of PRs. If your team updates dependencies on most PRs (e.g. via automated Dependabot PRs that land multiple times per week), the hit rate will be lower. Check how frequently package-lock.json appears in your merged PR history before committing to the projected recovery.
  • Verify
    The filesystem scan misses OS package vulnerabilities in the base image. The Turn 5 optimisation deliberately trades full coverage for speed on PR runs, relying on the weekly scan for base image coverage. If your security policy or compliance requirements mandate full image scanning on every commit — particularly for a payment service — this tradeoff is not available to you. Confirm the policy before deploying the filesystem scan configuration.
  • Verify
    Removing max-parallel: 1 doubles concurrent runner usage. If the pipeline runs on self-hosted runners with a fixed pool, removing the concurrency limit may cause queuing rather than true parallelism if the runner pool is already at capacity. On GitHub-hosted runners, this is not an issue — runners are provisioned on demand. Verify your runner type before removing the limit.
  • Note
    Implement fixes one at a time and measure. The Turn 2 ranking recommends deploying in rank order with measurement between each fix. This is not just good practice — it is the only way to validate the projections. The cache hit rate recovery is visible in the GitHub Actions cache tab within 10 runs. Measure it before deploying the parallelisation change, so the contribution of each fix is independently attributable. Combined deployment makes it impossible to know which fix had which effect.
Prompting tip for gradual degradation triage
Provide timing history, not just the current state. The current job log showed that npm ci takes 11 minutes. The timing history showed it took 2 minutes six months ago and grew gradually. The history is what makes the cache miss rate the primary cause — without it, the obvious hypothesis is "the install is slow because we have more packages," which is a symptom, not the cause. For any performance regression that occurred gradually rather than discretely, a time-series view of the metric is as important as the current value.
