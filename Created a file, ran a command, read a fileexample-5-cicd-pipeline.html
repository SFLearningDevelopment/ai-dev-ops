Step 1 of 5
The problem

The payment-api service now has a Dockerfile (Example 1) and a basic CI pipeline (Example 3). Both were Tier 1 single-file tasks. The team now needs a production-grade end-to-end CI/CD pipeline — one that builds, scans for vulnerabilities, pushes to ECR, deploys to EKS, and enforces security gates between stages. Three other service teams will adopt this pipeline as their standard.

This is the first Tier 2 example. Unlike Tier 1, the output is not one file — it is a system of files that must work together coherently. The naive approach's failure modes are integration gaps between files, not just weaknesses within a single file.

Requirements
— Build stage: Docker image build, layer cache via BuildKit, image tagged with git SHA and branch name
— Scan stage: Trivy vulnerability scan on the built image, CRITICAL findings block the pipeline, HIGH findings produce a warning report
— Push stage: ECR push only if scan passes, OIDC auth, image digest captured as output
— Deploy stage: kubectl set image on the EKS deployment, rollout status verified, automatic rollback if rollout fails
— Approval gate: prod deployments require manual approval after scan, before push
— Scan report: Trivy JSON output uploaded as a GitHub Actions artifact, retained 30 days
— All secrets via OIDC — no long-lived AWS or Kubernetes credentials
— Trivy config as a separate .trivy.yaml file, not inline flags
Files involved in this example
File Purpose Stage
.github/workflows/cicd.yml Main pipeline — build, scan, push, deploy jobs with approval gate Build · Push · Deploy
.trivy.yaml Trivy scanner configuration — severity thresholds, ignore rules, output format Scan
k8s/deployment.yaml Kubernetes deployment manifest — the target of the kubectl set image deploy step Deploy
k8s/rollback.sh Rollback script — triggered automatically if rollout status check fails Deploy

Step 2 of 5
The naive approach

The naive pipeline is assembled from three sources: the basic CI workflow from Example 3, a Trivy scan step copied from a blog post, and a deploy step from an internal wiki. Each piece works in isolation. The integration between them does not.

.github/workflows/cicd.yml (naive)
name: CI/CD

on:
  push:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build image
        run: docker build -t payment-api:${{ github.sha }} .

  scan:
    runs-on: ubuntu-latest
    # No dependency on build — image may not exist yet
    steps:
      - name: Scan image
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: payment-api:${{ github.sha }}
          format: table
          # No severity threshold — scan never blocks the pipeline
          exit-code: 0

  push:
    runs-on: ubuntu-latest
    # No dependency on scan — pushes even if scan finds CRITICAL vulns
    steps:
      - uses: actions/checkout@v4
      - name: Configure AWS
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ap-south-1
      - name: Push to ECR
        run: |
          docker tag payment-api:${{ github.sha }} $ECR_REGISTRY/payment-api:${{ github.sha }}
          docker push $ECR_REGISTRY/payment-api:${{ github.sha }}

  deploy:
    runs-on: ubuntu-latest
    # No dependency on push — kubectl may reference image that doesn't exist in ECR
    steps:
      - name: Deploy
        run: |
          kubectl set image deployment/payment-api \
            payment-api=$ECR_REGISTRY/payment-api:${{ github.sha }}
          # No rollout status check — deploy job succeeds even if pods crash

Six integration failures — not file-level weaknesses but system-level gaps:

  • Integration
    Jobs run in parallel with no dependency chain. scan runs without waiting for build, so the image it scans may not exist yet. deploy runs without waiting for push, so it may reference an image that has not reached ECR. The pipeline appears to have four stages — it actually has four independent jobs that happen to run simultaneously.
  • Security
    Trivy exit-code: 0 means the scan never blocks anything. The scan runs, prints a table, and exits successfully regardless of what it finds. CRITICAL vulnerabilities are logged and ignored. The scan is theatre — it creates the appearance of security gating without providing any.
  • Security
    Long-lived AWS credentials. AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY — static, never-expiring, stored as repository secrets. Repeating the failure mode from Example 3's naive approach, now in a more critical position: these credentials have ECR push access to production images.
  • Correctness
    No rollout status check after deploy. kubectl set image submits the rollout request and exits 0 — it does not wait for pods to become healthy. A bad image that causes CrashLoopBackOff will produce a successful deploy job. The pipeline goes green; the service is down.
  • Correctness
    No approval gate between scan and prod push. A CRITICAL finding is logged (once the exit-code is fixed) but the pipeline continues automatically to push and deploy. There is no human checkpoint between "we know there is a critical vulnerability" and "we are deploying it to production".
  • Correctness
    No scan report artifact. The Trivy output is printed to the job log and lost when the log expires. There is no persisted, searchable record of what vulnerabilities existed in each deployed image — which is a compliance requirement in most regulated environments.
The core problem
The naive pipeline has the structural shape of a CI/CD system — four named stages — but none of the integration logic that makes those stages a system. Each job is a standalone script. The dependency chain, the security gate, the rollout verification, and the audit trail are all missing. It does not fail; it succeeds at doing the wrong things in the wrong order.

Turns 1 2 3 4 5
Turn 1 of 5 — Pipeline with correct job dependency chain and OIDC
Engineer → Claude Code

Generate a GitHub Actions CI/CD workflow for payment-api. Four jobs in strict sequence: build → scan → push → deploy. Requirements:

build: Docker build with BuildKit enabled, tag with github.sha and github.ref_name, cache layers using type=gha cache
scan: Trivy scan on the built image, config from .trivy.yaml, exit-code 1 on CRITICAL findings
push: ECR push via OIDC (role ARN from secrets.AWS_ROLE_ARN), region ap-south-1, capture image digest as job output
deploy: kubectl set image using the digest from push, rollout status check with 3-minute timeout, automatic rollback on failure
Approval gate between scan and push for runs targeting main. Actions versions: checkout@v4, configure-aws-credentials@v4, amazon-ecr-login@v2.

Claude Code
.github/workflows/cicd.yml (turn 1) 
name: CI/CD — payment-api

on:
  push:
    branches: [ main ]
  pull_request:

permissions:
  contents: read

env:
  IMAGE_NAME: payment-api
  AWS_REGION: ap-south-1

jobs:
  # ── 1. Build ─────────────────────────────────────────────────────────
  build:
    name: Build image
    runs-on: ubuntu-latest
    outputs:
      image-tag: ${{ steps.meta.outputs.tag }}
    steps:
      - uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Set image metadata
        id: meta
        run: echo "tag=${{ github.sha }}-${{ github.ref_name }}" >> $GITHUB_OUTPUT

      - name: Build and export to Docker daemon
        uses: docker/build-push-action@v5
        with:
          context: .
          push: false
          load: true   # Load into local daemon for Trivy to scan
          tags: ${{ env.IMAGE_NAME }}:${{ steps.meta.outputs.tag }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  # ── 2. Scan ──────────────────────────────────────────────────────────
  scan:
    name: Security scan
    runs-on: ubuntu-latest
    needs: build
    steps:
      - uses: actions/checkout@v4

      - name: Rebuild image for scanning
        uses: docker/build-push-action@v5
        with:
          context: .
          push: false
          load: true
          tags: ${{ env.IMAGE_NAME }}:${{ needs.build.outputs.image-tag }}
          cache-from: type=gha   # Full cache hit — no rebuild cost

      - name: Run Trivy scan
        uses: aquasecurity/trivy-action@0.28.0
        with:
          image-ref: ${{ env.IMAGE_NAME }}:${{ needs.build.outputs.image-tag }}
          trivy-config: .trivy.yaml
          output: trivy-report.json

      - name: Upload scan report
        if: always()   # Upload even if scan fails — report is the evidence
        uses: actions/upload-artifact@v4
        with:
          name: trivy-report-${{ github.sha }}
          path: trivy-report.json
          retention-days: 30

  # ── 3. Approve (prod only) ────────────────────────────────────────────
  approve:
    name: Approval gate
    runs-on: ubuntu-latest
    needs: scan
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    environment:
      name: production   # Required reviewers configured in repo settings

    steps:
      - name: Approval checkpoint
        run: echo "Scan passed. Proceeding to ECR push after approval."

  # ── 4. Push ──────────────────────────────────────────────────────────
  push:
    name: Push to ECR
    runs-on: ubuntu-latest
    needs: [ scan, approve ]
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    permissions:
      contents: read
      id-token: write
    outputs:
      image-digest: ${{ steps.push.outputs.digest }}
      image-uri: ${{ steps.login-ecr.outputs.registry }}/${{ env.IMAGE_NAME }}:${{ needs.build.outputs.image-tag }}

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}

      - name: Login to ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Build and push with digest capture
        id: push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.login-ecr.outputs.registry }}/${{ env.IMAGE_NAME }}:${{ needs.build.outputs.image-tag }}
          cache-from: type=gha
          provenance: false   # Disable provenance attestation for ECR compatibility

  # ── 5. Deploy ─────────────────────────────────────────────────────────
  deploy:
    name: Deploy to EKS
    runs-on: ubuntu-latest
    needs: push
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    permissions:
      contents: read
      id-token: write

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}

      - name: Update kubeconfig for EKS
        run: aws eks update-kubeconfig --name payment-api-cluster --region ${{ env.AWS_REGION }}

      - name: Deploy image
        id: deploy
        run: |
          kubectl set image deployment/payment-api \
            payment-api=${{ needs.push.outputs.image-uri }} \
            -n payment

      - name: Verify rollout
        id: rollout
        run: |
          kubectl rollout status deployment/payment-api \
            -n payment \
            --timeout=180s

      - name: Rollback on failure
        if: failure() && steps.rollout.conclusion == 'failure'
        run: bash k8s/rollback.sh payment-api payment

Three decisions worth noting:

— needs: [scan, approve] on the push job means both the scan passing AND a human approving are required. If the scan fails, the approve job never triggers, so the pipeline is blocked at two independent gates — not just the human approval.

— if: always() on the artifact upload means the Trivy report is uploaded even when the scan fails and blocks the pipeline. The report is the evidence for why the pipeline was blocked — losing it on failure would defeat the audit purpose.

— provenance: false on the ECR push: Docker Build Push Action v5 enables provenance attestations by default, which creates multi-platform image manifests. ECR handles these inconsistently and the digest output becomes unreliable. Disabling provenance produces a clean single-manifest image and a reliable digest that the deploy job can reference.

Turn 2 of 5 — Trivy configuration file
Engineer → Claude Code

Generate the .trivy.yaml config file. Requirements:

— Format: JSON (for artifact upload and machine parsing)
— Severity: CRITICAL blocks pipeline (exit-code 1), HIGH produces report but does not block
— Ignore unfixed vulnerabilities — we can only fix what has a patch available
— Scan OS packages and application dependencies (npm)
— Skip known false positives: CVE-2023-44487 (HTTP/2 Rapid Reset — mitigated at load balancer)
— Timeout: 5 minutes

Claude Code
.trivy.yaml (turn 2) 
# Trivy configuration for payment-api CI/CD pipeline
# Docs: https://aquasecurity.github.io/trivy/latest/docs/references/configuration/config-file/

image:
  removed-pkgs: true   # Report packages removed from final image layers

scan:
  security-checks:
    - vuln        # OS and library vulnerabilities
    - secret      # Secrets accidentally baked into image layers

vulnerability:
  ignore-unfixed: true   # Skip vulns with no available patch
  type:
    - os          # Alpine/Debian OS packages
    - library     # npm and other language packages

format: json
output: trivy-report.json

severity:
  - CRITICAL    # Blocks pipeline (exit-code 1 via action config)
  - HIGH        # Reported but does not block

timeout: 5m0s

ignorefile: .trivyignore.yaml
.trivyignore.yaml (CVE suppression list) 
vulnerabilities:
  - id: CVE-2023-44487
    reason: HTTP/2 Rapid Reset — mitigated at load balancer layer. Not exploitable via this service.
    expires: 2025-12-31   # Review suppression annually

Two notes on the config split: the ignorefile reference keeps CVE suppressions in a separate file from scanner config. This is important for auditability — reviewers can see exactly which CVEs are suppressed and why without reading scanner configuration. The expires field forces annual review of whether the suppression is still justified.

On severity: Trivy's severity config controls which severities are reported. The exit-code behaviour (CRITICAL blocks, HIGH does not) is controlled by the exit-code and exit-on-eol settings in the GitHub Actions step — not in this config file. The workflow from Turn 1 handles this correctly via the action's trivy-config input pointing at this file.

Generate k8s/rollback.sh — the script that the pipeline calls on rollout failure. It should undo the deployment, verify the rollback succeeded, and output a clear summary of what it did.

Claude Code

Exit code 137 is OOMKilled — the container was killed by the kernel because it exceeded its memory limit (512Mi in the manifest). The CrashLoopBackOff is a consequence, not the root cause. Before deploying again, increase the memory limit or profile the application's actual consumption. The rollback script will restore the previous working version immediately.

k8s/rollback.sh (turn 4) 
#!/usr/bin/env bash
# k8s/rollback.sh — Automated rollback on deployment failure
# Usage: ./rollback.sh DEPLOYMENT_NAME NAMESPACE
# Called by the deploy job when rollout status times out.
set -euo pipefail

readonly DEPLOYMENT="${1:?DEPLOYMENT_NAME required}"
readonly NAMESPACE="${2:?NAMESPACE required}"
readonly ROLLBACK_TIMEOUT=120

echo "[ROLLBACK] Initiating rollback for $DEPLOYMENT in $NAMESPACE"
echo "[ROLLBACK] Current image: $(kubectl get deployment "$DEPLOYMENT" -n "$NAMESPACE" -o jsonpath='{.spec.template.spec.containers[0].image}')"

# Capture the previous revision for the summary
PREV_REVISION=$(kubectl rollout history deployment/"$DEPLOYMENT" \
  -n "$NAMESPACE" --no-headers | tail -2 | head -1 | awk '{print $1}')

# Execute rollback
kubectl rollout undo deployment/"$DEPLOYMENT" -n "$NAMESPACE"

# Verify rollback completes within timeout
echo "[ROLLBACK] Waiting for rollback to complete (timeout: ${ROLLBACK_TIMEOUT}s)..."
if kubectl rollout status deployment/"$DEPLOYMENT" \
    -n "$NAMESPACE" \
    --timeout="${ROLLBACK_TIMEOUT}s"; then
  RESTORED_IMAGE=$(kubectl get deployment "$DEPLOYMENT" \
    -n "$NAMESPACE" \
    -o jsonpath='{.spec.template.spec.containers[0].image}')
  echo "[ROLLBACK] SUCCESS — restored to revision $PREV_REVISION"
  echo "[ROLLBACK] Active image: $RESTORED_IMAGE"
  exit 0
else
  echo "[ROLLBACK] FAILED — rollback did not complete within ${ROLLBACK_TIMEOUT}s" >&2
  echo "[ROLLBACK] Manual intervention required. Check: kubectl describe deployment $DEPLOYMENT -n $NAMESPACE" >&2
  exit 1
fi

On the OOMKilled root cause: exit code 137 = SIGKILL from the OOM killer. The container hit 512Mi and was terminated. Next steps: (1) run kubectl top pods -n payment during normal operation to establish actual memory usage, (2) increase the limit to 150% of the observed peak, (3) re-deploy. The rollback restores service immediately; the resource limit fix is a separate change.

Four files, working as a system. Here is the key diff from naive to final, followed by a map of how the files connect — the integration points that make this a pipeline rather than four independent scripts.

Naive → final: system-level changes

How the four files connect
.trivy.yaml →
Referenced by cicd.yml scan job via trivy-config: .trivy.yaml. Controls severity thresholds, output format, and the ignore file reference. If this file is absent, the scan step uses Trivy defaults — which do not match the team's security policy and do not produce JSON output for the artifact.
.trivyignore.yaml →
Referenced by .trivy.yaml via ignorefile. Suppresses specific CVEs with documented reasons and expiry dates. Keeping this separate from the scanner config means security suppressions are independently reviewable and auditable.
cicd.yml push job →
Outputs image-uri to the deploy job via needs.push.outputs.image-uri. The deploy job never constructs the image URI itself — it receives it from the push job. This ensures the deployed image is exactly what was scanned and approved, not a re-derived URI that could drift if tag naming logic changes.
k8s/deployment.yaml →
Container name payment-api must match the deploy job's kubectl set image command. The manifest's spec.containers[0].name is the key in the set image command: kubectl set image ... payment-api=NEW_IMAGE. A name mismatch silently applies no change — the old image continues running with no error.
k8s/rollback.sh →
Called by cicd.yml deploy job on rollout failure via if: failure() && steps.rollout.conclusion == 'failure'. Receives deployment name and namespace as arguments — both must match the deploy job's values. The script is tested by the Turn 4 failure; it is not hypothetical automation.

Step 5 of 5
Watch out

Claude Code produced a coherent four-file system across five turns. Here is what it handled correctly and what your specific environment must still verify.

What Claude Code handled well
Strict job dependency chain, if: always() on artifact upload so the scan report survives a scan failure, provenance: false for ECR digest reliability, dual gates (scan + approve) before push, image URI flowing from push to deploy via job outputs (never re-derived), kubectl set image container name alignment warning, exit code 137 = OOMKilled diagnosis from raw kubectl output, targeted convention fixes in Turn 5 without full file regeneration.
  • Verify
    The production environment must be configured in GitHub repository settings. The approval gate works via GitHub Environments — if the production environment does not exist in Settings → Environments, the approve job will run without requiring any reviewers. Create the environment and add required reviewers before the pipeline is considered production-ready.
  • Verify
    The EKS cluster name is hardcoded in the deploy job. aws eks update-kubeconfig --name payment-api-cluster assumes this exact cluster name. Claude Code used a reasonable default; your cluster name may differ. This will fail silently — the kubeconfig update succeeds with a different cluster name, and kubectl set image may target the wrong cluster.
  • Verify
    The rollback script requires kubectl rollout history access. The IAM role used for deploy needs RBAC permissions to read rollout history, not just set images. If the role has narrow permissions, the kubectl rollout history call in rollback.sh will fail before the actual rollback runs. Test the rollback script manually against your cluster before relying on it in production.
  • Verify
    The OOMKilled root cause from Turn 4 requires a separate fix. The rollback restored service, but the memory limit of 512Mi was insufficient for this service's actual usage. Run kubectl top pods -n payment during a representative load period, set the limit to 150% of the observed peak, and redeploy before the next feature release. The pipeline will produce the same OOMKilled failure until the limit is corrected.
  • Verify
    Trivy CVE suppression expiry dates require a review process. The .trivyignore.yaml sets expires: 2025-12-31 for CVE-2023-44487. Trivy does not enforce this expiry automatically — it is a documentation convention, not a hard gate. Add a calendar reminder or a CI check that fails if any suppression has passed its expiry date.
  • Note
    The scan job rebuilds the image rather than sharing it between jobs. GitHub Actions jobs run on separate runners with no shared filesystem. The scan job uses cache-from: type=gha to get a full cache hit — no layers are re-downloaded — but the build step must still run. This is correct behaviour; a zero-cost cache hit is the efficient path. If your cache hit rate is low, check that the cache-to: type=gha,mode=max in the build job is actually populating the cache.
Prompting tip for multi-file pipelines
In Tier 1, single-file prompts were self-contained. In Tier 2, the most important addition to every prompt is naming the integration contract explicitly — what one file produces that another file consumes. In Turn 3, specifying "the container name must match what the pipeline references" produced a correctly aligned manifest with a warning comment. Without that constraint, Claude Code would have used a reasonable default name that might not match — and the failure would have been silent.
