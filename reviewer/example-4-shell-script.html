Step 1 of 5
The problem

The payment-api service is now containerised and has a CI/CD pipeline. The final missing piece is a pre-deployment health check script — a bash script that runs before the new version is cut over in the CD pipeline, verifies the new pods are healthy, and blocks the cutover if they are not. If it blocks, it should not leave the cluster in a partially modified state.

Requirements
— Check that a given Kubernetes deployment reaches Available status within a configurable timeout
— Poll the /health endpoint of each new pod directly to confirm application-level readiness
— Accept deployment name, namespace, and timeout as arguments with sensible defaults
— Output structured PASS / FAIL per check with a timestamp
— Exit with code 0 only if all checks pass — exit 1 on any failure
— Be idempotent — safe to run multiple times without side effects
— Run on both macOS and Linux (the script is used locally by engineers and in CI)

The idempotency and cross-platform requirements are what separate this from a quick one-off script. A script that works once in CI but breaks on a re-run or behaves differently on a developer's MacBook is worse than no script at all — it breeds distrust in the tooling.

Step 2 of 5
The naive approach

Here is the script most engineers write from memory when they need a deployment check quickly. It works on a happy path, fails unpredictably everywhere else.

check-deployment.sh (naive) bash 
#!/bin/bash

DEPLOYMENT=$1
NAMESPACE=$2
TIMEOUT=60

# Wait for rollout
kubectl rollout status deployment/$DEPLOYMENT \
  -n $NAMESPACE \
  --timeout=${TIMEOUT}s

# Get pod IPs and check /health on each
PODS=$(kubectl get pods -n $NAMESPACE \
  -l app=$DEPLOYMENT \
  -o jsonpath='{.items[*].status.podIP}')

for pod in $PODS; do
  curl http://$pod:3000/health
done

echo "Deployment check complete"

This script will silently succeed in situations where it should fail. Here are its six critical problems:

  • Safety
    No set -euo pipefail. Without these flags: -e means the script continues executing after any command fails; -u means unset variables expand to empty string silently (so kubectl ... -n "" queries the wrong namespace without error); -o pipefail means a failed command in a pipeline is hidden by a succeeding one. A script without these three flags can exit 0 while having done nothing useful.
  • Correctness
    No argument validation. If called without arguments, DEPLOYMENT and NAMESPACE are empty strings. kubectl rollout status deployment/ returns a confusing API error. The script should validate required arguments before doing any work and print a usage message on failure.
  • Correctness
    Pod IP loop is fragile. kubectl get pods ... -o jsonpath='{.items[*].status.podIP}' returns IPs space-separated on a single line. The for pod in $PODS loop works — but only because of unquoted variable expansion. If any pod IP contains spaces (it won't, but the pattern is fragile), or if the list is empty, the loop silently skips. More importantly: pod IPs are not directly accessible from outside the cluster. This will always fail in CI.
  • Correctness
    curl exit code is ignored. Even if curl returns a non-200 response or times out, the script continues and exits 0. The health check result is printed to stdout but never acted on. The script reports "complete" regardless of whether any pod is actually healthy.
  • Portability
    Not cross-platform. GNU date, GNU timeout, and several kubectl jsonpath expressions behave differently on macOS (BSD tools). The script will work in Linux CI but fail on a developer's MacBook without a clear error message.
  • Observability
    No structured output. "Deployment check complete" is printed regardless of outcome. There is no per-check PASS/FAIL, no timestamp, no exit code reflecting actual health. A CD pipeline using this script has no way to distinguish a healthy deployment from a failed one.
The core problem
The naive script gives the appearance of verification without actually verifying anything. It will exit 0 on an unhealthy deployment, a missing deployment, an empty pod list, and a timed-out rollout — as long as kubectl rollout status doesn't fail. That is the worst kind of script: it provides false confidence.

Turn 1 of 3 — Initial generation
Engineer → Claude Code

Write a bash script called check-deployment.sh that verifies a Kubernetes deployment is healthy before a CD pipeline proceeds with cutover. Requirements:

— Arguments: DEPLOYMENT_NAME (required), NAMESPACE (required), TIMEOUT_SECONDS (optional, default 120)
— Check 1: kubectl rollout status succeeds within timeout
— Check 2: all pods matching app=DEPLOYMENT_NAME label show Running and Ready status via kubectl, not direct curl (pods are not directly reachable from CI)
— Check 3: desired replica count matches ready replica count from deployment status
— Output: timestamped PASS/FAIL per check, final summary
— Exit 0 only if all checks pass, exit 1 on any failure
— Must work on both macOS and Linux
— set -euo pipefail, full argument validation, usage message on bad input

Claude Code
check-deployment.sh (turn 1 output) 
#!/usr/bin/env bash
# check-deployment.sh — Pre-cutover deployment health verification
# Usage: ./check-deployment.sh DEPLOYMENT_NAME NAMESPACE [TIMEOUT_SECONDS]
set -euo pipefail

# ── Constants ────────────────────────────────────────────────────────────────
readonly SCRIPT_NAME="$(basename "$0")"
readonly DEFAULT_TIMEOUT=120
PASS_COUNT=0
FAIL_COUNT=0

# ── Helpers ──────────────────────────────────────────────────────────────────
usage() {
  echo "Usage: $SCRIPT_NAME DEPLOYMENT_NAME NAMESPACE [TIMEOUT_SECONDS]"
  echo ""
  echo "  DEPLOYMENT_NAME   Name of the Kubernetes deployment to verify"
  echo "  NAMESPACE         Kubernetes namespace containing the deployment"
  echo "  TIMEOUT_SECONDS   Rollout wait timeout (default: $DEFAULT_TIMEOUT)"
  echo ""
  echo "Exit codes: 0 = all checks passed, 1 = one or more checks failed"
  exit 1
}

timestamp() {
  # ISO 8601 compatible on both GNU date (Linux) and BSD date (macOS)
  date -u '+%Y-%m-%dT%H:%M:%SZ'
}

log_pass() {
  PASS_COUNT=$(( PASS_COUNT + 1 ))
  echo "[$(timestamp)] PASS  $1"
}

log_fail() {
  FAIL_COUNT=$(( FAIL_COUNT + 1 ))
  echo "[$(timestamp)] FAIL  $1" >&2
}

log_info() {
  echo "[$(timestamp)] INFO  $1"
}

# ── Argument validation ───────────────────────────────────────────────────────
if [[ $# -lt 2 ]]; then
  echo "Error: DEPLOYMENT_NAME and NAMESPACE are required." >&2
  usage
fi

readonly DEPLOYMENT="$1"
readonly NAMESPACE="$2"
readonly TIMEOUT="${3:-$DEFAULT_TIMEOUT}"

# Validate timeout is a positive integer
if ! [[ "$TIMEOUT" =~ ^[0-9]+$ ]] || [[ "$TIMEOUT" -eq 0 ]]; then
  echo "Error: TIMEOUT_SECONDS must be a positive integer, got: '$TIMEOUT'" >&2
  usage
fi

# Verify kubectl is available
if ! command -v kubectl &>/dev/null; then
  echo "Error: kubectl not found in PATH" >&2
  exit 1
fi

log_info "Checking deployment '$DEPLOYMENT' in namespace '$NAMESPACE' (timeout: ${TIMEOUT}s)"

# ── Check 1: Rollout status ───────────────────────────────────────────────────
log_info "Check 1: kubectl rollout status"
if kubectl rollout status deployment/"$DEPLOYMENT" \
    -n "$NAMESPACE" \
    --timeout="${TIMEOUT}s" &>/dev/null; then
  log_pass "Rollout completed within ${TIMEOUT}s"
else
  log_fail "Rollout did not complete within ${TIMEOUT}s"
fi

# ── Check 2: All pods Running and Ready ───────────────────────────────────────
log_info "Check 2: Pod readiness"
NOT_READY=$(kubectl get pods \
  -n "$NAMESPACE" \
  -l "app=$DEPLOYMENT" \
  --field-selector='status.phase!=Running' \
  -o name 2>/dev/null | wc -l | tr -d ' ')

if [[ "$NOT_READY" -eq 0 ]]; then
  log_pass "All pods are in Running phase"
else
  log_fail "$NOT_READY pod(s) not in Running phase"
fi

# Check Ready condition specifically (separate from phase)
NOT_READY_CONDITION=$(kubectl get pods \
  -n "$NAMESPACE" \
  -l "app=$DEPLOYMENT" \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .status.conditions[?(@.type=="Ready")]}{.status}{"\n"}{end}{end}' \
  2>/dev/null | grep -c 'False' || true)

if [[ "$NOT_READY_CONDITION" -eq 0 ]]; then
  log_pass "All pods have Ready=True condition"
else
  log_fail "$NOT_READY_CONDITION pod(s) have Ready=False condition"
fi

# ── Check 3: Desired vs ready replicas ────────────────────────────────────────
log_info "Check 3: Replica count"
DESIRED=$(kubectl get deployment "$DEPLOYMENT" \
  -n "$NAMESPACE" \
  -o jsonpath='{.spec.replicas}' 2>/dev/null)

READY=$(kubectl get deployment "$DEPLOYMENT" \
  -n "$NAMESPACE" \
  -o jsonpath='{.status.readyReplicas}' 2>/dev/null)

# readyReplicas may be absent (null) if zero pods are ready
READY="${READY:-0}"

if [[ "$DESIRED" -gt 0 ]] && [[ "$READY" -eq "$DESIRED" ]]; then
  log_pass "Ready replicas ($READY) matches desired ($DESIRED)"
else
  log_fail "Ready replicas ($READY) does not match desired ($DESIRED)"
fi

# ── Summary ───────────────────────────────────────────────────────────────────
echo ""
echo "─────────────────────────────────────────────────"
echo "  PASSED: $PASS_COUNT"
echo "  FAILED: $FAIL_COUNT"
echo "─────────────────────────────────────────────────"

if [[ "$FAIL_COUNT" -gt 0 ]]; then
  log_info "Result: UNHEALTHY — deployment '$DEPLOYMENT' failed $FAIL_COUNT check(s)"
  exit 1
fi

log_info "Result: HEALTHY — all checks passed for deployment '$DEPLOYMENT'"
exit 0

Key decisions:

— #!/usr/bin/env bash instead of #!/bin/bash: on macOS, /bin/bash is Bash 3.2 (2007). /usr/bin/env bash picks up the Homebrew-installed Bash 5.x if present, which supports [[ ]] reliably and handles associative arrays. For a script this simple it doesn't matter — but the pattern is correct and consistent.

— The grep -c ... || true pattern on the Ready condition check: grep -c exits 1 if it finds zero matches, which would trigger set -e and abort the script. The || true suppresses that exit — we want zero matches to be a valid result (all pods are ready), not an error.

— READY="${READY:-0}": kubectl omits readyReplicas from the JSON when the value is 0. Without this default, the comparison [[ "$READY" -eq "$DESIRED" ]] would error on an empty string.

— Failure output goes to stderr (>&2) and success to stdout. This means a CI system capturing stdout will get clean structured output, while stderr carries the failure detail that shows up in the job log.

Turn 2 of 3 — macOS failure pasted back verbatim

An engineer runs the script on their MacBook before pushing. It fails at the argument validation step with an unexpected error. They paste the exact stderr output.

Engineer → Claude Code

Script fails on macOS at the timeout validation step. Exact error (verbatim):

stderr on macOS (Apple Silicon, zsh terminal)
./check-deployment.sh: line 54: [[: 120: syntax error: invalid arithmetic operator (error token is "120")

Line 54 is: if [[ "$TIMEOUT" -eq 0 ]]; then

Running macOS 14 Sonoma. The bash --version in the terminal is 3.2.57 despite having bash 5 installed via Homebrew — the script is being invoked with the system bash, not the Homebrew one.

Claude Code

The issue is that Bash 3.2 does not support arithmetic comparison with -eq inside [[ ]] when the variable is a string that matches a number. The [[ ]] construct in Bash 3.2 treats the right-hand side of -eq as a string token and errors on values it can't parse in its specific context.

The immediate cause is that the script uses #!/usr/bin/env bash, which resolves to /bin/bash (3.2) on macOS when run directly as ./check-deployment.sh — the PATH lookup finds the system bash before Homebrew's. The fix has two parts:

Fix 1: Replace the mixed [[ ]] arithmetic comparison with pure arithmetic context:

Fix — timeout validation (Bash 3.2 compatible) 
# Before (Bash 5 only):
if ! [[ "$TIMEOUT" =~ ^[0-9]+$ ]] || [[ "$TIMEOUT" -eq 0 ]]; then

# After (Bash 3.2 compatible):
if ! [[ "$TIMEOUT" =~ ^[0-9]+$ ]]; then
  echo "Error: TIMEOUT_SECONDS must be a positive integer, got: '$TIMEOUT'" >&2
  usage
fi
if (( TIMEOUT == 0 )); then
  echo "Error: TIMEOUT_SECONDS must be greater than 0" >&2
  usage
fi

Fix 2: Add a Bash version check at the top of the script so the error is explicit rather than cryptic when invoked with the system bash:

Add after shebang — Bash version guard 
# Require Bash >= 3.2 — split checks to avoid the very bug we're guarding against
BASH_MAJOR="${BASH_VERSINFO[0]}"
BASH_MINOR="${BASH_VERSINFO[1]}"
if (( BASH_MAJOR < 3 )) || { (( BASH_MAJOR == 3 )) && (( BASH_MINOR < 2 )); }; then
  echo "Error: Bash >= 3.2 required (found ${BASH_VERSINFO[0]}.${BASH_VERSINFO[1]})" >&2
  exit 1
fi

The (( )) arithmetic context works correctly in Bash 3.2 for integer comparisons, unlike [[ -eq ]] which has subtle parsing differences between versions. Apply both fixes and the script will behave identically on macOS system bash and Linux.

Turn 3 of 3 — Idempotency requirement added

The script works correctly on both platforms. A new requirement surfaces: the CD pipeline may re-run the health check up to three times with a backoff if the first check times out. The script must be explicitly idempotent — running it multiple times against the same deployment must produce the same result without side effects, and must support a --retry mode that loops internally.

Engineer → Claude Code

Add two things to the script:

1. An optional --retry N flag (default 1, max 5) that retries all checks up to N times with a 15-second backoff between attempts. Print attempt number. Exit 0 only if the final attempt passes all checks.

2. An explicit idempotency guard — a comment block at the top that documents what the script does and does NOT modify, so operators know it is safe to re-run. The script should also verify it has only read access to the cluster (no kubectl apply/delete calls anywhere) and emit a warning if run with a kubeconfig that has write permissions to the namespace.

Claude Code

On the permissions warning: checking write permissions before a read-only script is good practice but has a practical caveat. kubectl auth can-i will return true for cluster-admins even when the script itself never writes anything — so this is an advisory warning, not a hard block. The script will still run; it just informs operators of elevated permissions so they can decide whether to use a restricted kubeconfig for CI.

Here are the targeted additions — insert after argument validation, before Check 1:

Additions — retry logic and idempotency guard 
# ── Idempotency contract ─────────────────────────────────────────────────────
# This script is READ-ONLY. It:
#   - Reads deployment status and pod conditions via kubectl get/rollout
#   - Does NOT modify any Kubernetes resources
#   - Does NOT create, update, or delete any objects
#   - Does NOT write to any files outside /tmp
#   - Is safe to re-run any number of times against the same deployment
# Running this script multiple times will produce the same result as running
# it once, assuming the cluster state does not change between runs.

# ── Permissions advisory ──────────────────────────────────────────────────────
if kubectl auth can-i create pods -n "$NAMESPACE" &>/dev/null; then
  echo "[$(timestamp)] WARN  Current kubeconfig has write access to namespace '$NAMESPACE'." >&2
  echo "[$(timestamp)] WARN  Consider using a read-only kubeconfig for CI health checks." >&2
fi

# ── Retry configuration ───────────────────────────────────────────────────────
MAX_RETRIES=1

# Parse --retry flag (supports --retry N or --retry=N)
while [[ $# -gt 0 ]]; do
  case "$1" in
    --retry=*)
      MAX_RETRIES="${1#--retry=}"
      shift
      ;;
    --retry)
      MAX_RETRIES="$2"
      shift 2
      ;;
    *) shift ;;
  esac
done

if ! [[ "$MAX_RETRIES" =~ ^[0-9]+$ ]] || (( MAX_RETRIES < 1 )) || (( MAX_RETRIES > 5 )); then
  echo "Error: --retry must be an integer between 1 and 5, got: '$MAX_RETRIES'" >&2
  exit 1
fi

readonly RETRY_BACKOFF_SECONDS=15

# ── Run checks with retry ─────────────────────────────────────────────────────
run_checks() {
  PASS_COUNT=0
  FAIL_COUNT=0
  # ... all three checks from Turn 1 go here, unchanged ...
}

attempt=1
while (( attempt <= MAX_RETRIES )); do
  log_info "Attempt $attempt of $MAX_RETRIES"
  run_checks
  if [[ "$FAIL_COUNT" -eq 0 ]]; then
    log_info "Result: HEALTHY on attempt $attempt"
    exit 0
  fi
  if (( attempt < MAX_RETRIES )); then
    log_info "Attempt $attempt failed. Retrying in ${RETRY_BACKOFF_SECONDS}s..."
    sleep "$RETRY_BACKOFF_SECONDS"
  fi
  (( attempt++ )) || true   # (( expr )) exits 1 when result is 0; || true prevents set -e trigger
done

log_info "Result: UNHEALTHY after $MAX_RETRIES attempt(s). Failed $FAIL_COUNT check(s) on final attempt."
exit 1

Note the (( attempt++ )) || true comment — this is a subtle set -e trap. Arithmetic expressions in (( )) exit with status 1 when the result is 0 (falsy). When attempt increments from 0 to 1, the expression result is 1 (truthy) — fine. But if attempt ever evaluates to 0 after increment (it won't here, but the pattern is defensive), set -e would abort the script. The || true is the standard idiom to use arithmetic increment safely under set -e.

The refined output

Here is a side-by-side diff of the key structural differences between the naive script and the production-grade version. Every added line is a decision with a reason.

Naive → final: key structural differences
#!/bin/bash # system bash on macOS = 3.2 #!/usr/bin/env bash # picks up newer bash if installed set -euo pipefail # abort on error, unset vars, pipe failures DEPLOYMENT=$1 # unquoted, no validation NAMESPACE=$2 if [[ $# -lt 2 ]]; then usage; fi readonly DEPLOYMENT="$1" # quoted, validated, readonly readonly NAMESPACE="$2" readonly TIMEOUT="${3:-120}" kubectl rollout status ... # exit ignored, output mixed if kubectl rollout status ...; then log_pass "Rollout completed" else log_fail "Rollout timed out" # FAIL_COUNT incremented, not abort fi for pod in $PODS; do # direct curl — fails in CI curl http://$pod:3000/health done NOT_READY=$(kubectl get pods ... --field-selector ...) # kubectl only if [[ "$NOT_READY" -eq 0 ]]; then log_pass; else log_fail; fi echo "Deployment check complete" # always, regardless of outcome if [[ "$FAIL_COUNT" -gt 0 ]]; then exit 1; fi exit 0 # only if all checks passed
  • Safety
    set -euo pipefail at the top. The three flags work together: -e aborts on any unhandled non-zero exit; -u treats unset variables as errors (catches typos in variable names immediately); -o pipefail makes the exit code of a pipeline reflect the rightmost failing command, not the last one. Together they eliminate the silent-success failure mode that plagues naive scripts.
  • Correctness
    Checks are independent — a failure accumulates, not aborts. FAIL_COUNT is incremented on each failed check but the script continues to run all checks. This means the output always covers all three checks even when the first one fails, giving the operator a complete picture of the deployment's health rather than stopping at the first problem.
  • Portability
    Arithmetic via (( )), not [[ -eq ]]. After the Turn 2 fix, all integer comparisons use the arithmetic context, which behaves consistently across Bash 3.2 and 5.x. The timestamp function uses date -u '+%Y-%m-%dT%H:%M:%SZ' which works on both GNU date and BSD date without flags that differ between platforms.
  • Idempotency
    Explicit idempotency contract documented at the top. The comment block documents what the script reads and what it never writes. This is not just documentation — it is a commitment that future maintainers are expected to preserve. Any kubectl apply, kubectl delete, or file-write added later breaks the stated contract and should be challenged in code review.

Watch out

Claude Code produced a solid, portable, idempotent script across three turns. Here is what it handled correctly and what it genuinely cannot know without your cluster context.

What Claude Code handled well
set -euo pipefail discipline throughout, argument validation with usage message, structured PASS/FAIL output with timestamps to stdout/stderr separation, grep -c || true idiom for zero-match safety, READY="${READY:-0}" for missing JSON fields, (( attempt++ )) || true under set -e, the Bash 3.2 arithmetic bug from Turn 2 diagnosed precisely, and the permissions advisory correctly framed as a warning not a hard block.
  • Verify
    The pod label selector assumes app=DEPLOYMENT_NAME. Claude Code used -l "app=$DEPLOYMENT" because it's the most common Kubernetes label convention. Your deployments may use app.kubernetes.io/name, component, or a custom label instead. If the selector doesn't match your pods, Check 2 will return zero pods and pass incorrectly — which is exactly the silent success failure mode the script was designed to prevent. Verify the label before deploying.
  • Verify
    Check 3 replica count can be misleading during a rolling update. If the deployment is mid-rollout when the script runs, readyReplicas may be less than spec.replicas even if the rollout is progressing correctly. Check 1 (rollout status with timeout) is the authoritative gate — Check 3 is a secondary confirmation. If Check 1 passes but Check 3 fails, investigate before assuming the deployment is broken.
  • Verify
    The retry backoff is fixed at 15 seconds. Claude Code hardcoded 15 seconds as a reasonable default. For a deployment with a slow startup (JVM warmup, large model loading), 15 seconds may not be enough between attempts. Make RETRY_BACKOFF_SECONDS a configurable argument if your services have variable startup times.
  • Verify
    The permissions advisory requires kubectl auth can-i to work. In some cluster configurations or RBAC setups, kubectl auth can-i itself requires permissions that the CI kubeconfig may not have. If the advisory check fails with a permissions error, it will trigger set -e and abort the script before any health checks run. Wrap it in a subshell if this is a concern: if kubectl auth can-i ... 2>/dev/null; then.
  • Note
    The script tests Kubernetes-level readiness, not application-level correctness. A pod can be Running, Ready=True, and fully replicated while the application inside it is returning 500s on business logic endpoints. Kubernetes readiness probes verify that the container is ready to receive traffic — not that it is processing it correctly. For application-level verification, add a smoke test job after the health check in your CD pipeline.
Prompting tip for future shell scripts
The most productive pattern across all three turns was pasting exact stderr output, not descriptions of it. The Turn 2 Bash 3.2 bug was diagnosed in one turn because the exact error message, the exact line number, and the exact bash version were provided. Paraphrasing "it fails on Mac" would have produced a list of possible causes. The exact output produced a precise diagnosis. For shell scripts especially, error messages contain the signal — always paste them verbatim.

🔍 Reviewer question — E4-1
The naive shell script in Example 4 exits with code 0 even when the deployment is unhealthy. Which of the following is the PRIMARY mechanism that allows this to happen?
AThe script uses `curl` which always returns exit code 0
BThe script lacks `set -e` so it continues executing after command failures and always reaches the final `echo` which exits 0
CThe script has a syntax error that prevents it from checking the exit code
DKubernetes `rollout status` always returns 0 regardless of deployment health
Without `set -e`, a failing command does not abort the script. The `kubectl rollout status` can time out, curl can fail, and the script continues executing, reaching `echo 'Deployment check complete'` which exits 0. The absence of `set -euo pipefail` is the root cause of the false-confidence failure mode.
