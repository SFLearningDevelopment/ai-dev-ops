Multi-environment Terraform with remote state

Tier 2 — Multi-step workflow Infrastructure as Code 5-turn interaction 5 files · 3 environments

Step 1 of 5
The problem

The payment-api infrastructure needs to be provisioned across three environments — dev, staging, and prod — each with different resource sizes, different retention policies, and different access controls. The team currently runs Terraform locally with a single terraform.tfvars file that gets manually edited before each apply. State is stored locally. Two engineers have already applied conflicting changes by running Terraform simultaneously.

The task is to restructure the Terraform project to support multi-environment deployment safely: remote state with locking, per-environment variable files, and a module structure that enforces the separation between shared infrastructure logic and environment-specific configuration.

Requirements
— Remote state: S3 backend per environment, DynamoDB table for state locking
— Environment separation: dev, staging, prod each get their own state file and variable set
— Module structure: reusable module in /modules/rds — the variables.tf from Example 2 is its interface
— Environment configs: per-environment .tfvars files, no manual editing before apply
— Backend bootstrap: a one-time script to create the S3 bucket and DynamoDB table before Terraform can run
— State isolation: destroying dev must not be possible to accidentally affect prod state
— CI integration: the pipeline from Example 5 will run terraform plan on PRs and terraform apply on merge to main
Files involved in this example
FilePurposeLayer
backend.tf S3 backend configuration with per-environment key paths and DynamoDB locking State
modules/rds/main.tf Reusable RDS module — consumes the variables.tf interface from Example 2 Module
environments/dev.tfvars Dev environment variable values — small instance, short retention, no multi-AZ Environment
environments/staging.tfvars Staging environment variable values — medium instance, matches prod retention Environment
environments/prod.tfvars Prod environment variable values — large instance, multi-AZ, maximum retention Environment
scripts/bootstrap-state.sh One-time script to create S3 bucket and DynamoDB table before first Terraform run State

Step 2 of 5
The naive approach

The naive multi-environment approach is a single Terraform directory with a single state file, different .tfvars files manually selected at apply time, and no locking. It works until it doesn't — and when it fails, it fails in ways that are difficult to recover from.

Project structure (naive)
# Everything in one flat directory, one state file
infra/
├── main.tf
├── variables.tf
├── terraform.tfstate          # Local state — lost if machine dies
├── terraform.tfstate.backup
├── dev.tfvars                 # Manually selected at apply time
├── staging.tfvars
└── prod.tfvars                # One wrong command applies prod config to dev state
main.tf (naive) — no backend, hardcoded values leaking through
# No backend block — state is local
resource "aws_db_instance" "main" {
  identifier        = "payment-api-db"         # Hardcoded — same in every env
  engine            = "postgres"
  engine_version    = "15.4"
  instance_class    = var.instance_class
  allocated_storage = var.allocated_storage
  db_name           = "paymentdb"              # Hardcoded — not parameterised
  username          = "admin"                  # Hardcoded credential
  password          = var.db_password

  # No tags — impossible to identify which env this belongs to
  # No lifecycle rules — accidental destroy is not prevented
}

Five distinct failure modes — each one a real incident waiting to happen:

  • Safety
    Local state with no locking. Two engineers running terraform apply simultaneously against the same state file will corrupt it. Recovery requires manual state surgery — a high-stakes operation that often causes more damage than the original conflict. The team has already experienced this; it is the reason this restructure is happening.
  • Safety
    One state file for all environments. Running terraform apply -var-file=prod.tfvars against a state file that was last used with dev config causes Terraform to attempt to reconcile the state — potentially destroying dev resources and creating prod resources in the wrong account or region. There is no structural barrier between environments.
  • Correctness
    Hardcoded identifier and db_name. Every environment creates an RDS instance with the same name. In a shared AWS account, the second apply fails with a "DB instance already exists" error. In separate accounts, the naming gives no indication of which environment an instance belongs to, making cost allocation and incident response harder.
  • Safety
    No prevent_destroy lifecycle rule on prod. A terraform destroy or a plan that removes the RDS resource will execute without any additional confirmation. For a stateful resource holding production data, this is an unacceptable risk. Lifecycle rules are the Terraform-native mechanism to guard against this.
  • Correctness
    No environment-aware tagging. Every resource has the same tags regardless of which .tfvars file was used. Cost allocation by environment is impossible. When an incident occurs, identifying which environment a resource belongs to requires checking the AWS console manually.
The core problem
The naive structure treats multi-environment as a configuration problem — just use different .tfvars files. It is actually an isolation problem. Without separate state files, separate backends, and structural barriers between environments, the configuration difference between dev and prod is the only thing preventing a prod outage from a mistyped command. That is not a system; it is a hope.

Recommended directory structure
infra/
├── backend.tf                       # Backend config — key injected at init
├── main.tf                          # Root module — calls /modules/rds
├── variables.tf                     # Root variables — passed to module
├── outputs.tf                       # Root outputs — exposes module outputs
├── versions.tf                      # Provider version pins
├── environments/
│   ├── dev.tfvars                   # Dev-specific values
│   ├── staging.tfvars               # Staging-specific values
│   └── prod.tfvars                  # Prod-specific values
├── modules/
│   └── rds/
│       ├── main.tf                  # RDS resource definitions
│       ├── variables.tf             # Module interface (from Example 2)
│       └── outputs.tf               # Module outputs
└── scripts/
    └── bootstrap-state.sh           # One-time S3 + DynamoDB creation

The key design decision: the backend key is omitted from backend.tf and injected at init time via -backend-config="key=payment-api/dev/terraform.tfstate". This means the same committed backend.tf is used for all environments — the environment is never hardcoded in a file that gets committed. The CI pipeline (Example 5) injects the correct key based on the target environment as a pipeline variable.

Turn 2 of 5 — RDS module wired to the Example 2 interface

— RDS instance identifier must include the environment name to avoid cross-environment naming collisions

Claude Code
modules/rds/main.tf (turn 2)
# modules/rds/main.tf
# Variable interface: modules/rds/variables.tf (from Example 2)
# All 14 variables are consumed here — none are hardcoded.

# ── Security group ───────────────────────────────────────────────────────────
resource "aws_security_group" "rds" {
  name_prefix = "${var.identifier}-rds-"
  vpc_id      = var.vpc_id
  description = "RDS access for ${var.identifier}"

  dynamic "ingress" {
    for_each = var.allowed_cidr_blocks
    content {
      from_port   = 5432
      to_port     = 5432
      protocol    = "tcp"
      cidr_blocks = [ingress.value]
    }
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = merge(var.tags, { Name = "${var.identifier}-rds-sg" })

  lifecycle {
    create_before_destroy = true
  }
}

# ── DB subnet group ───────────────────────────────────────────────────────────
resource "aws_db_subnet_group" "main" {
  name       = "${var.identifier}-subnet-group"
  subnet_ids = var.subnet_ids
  tags       = merge(var.tags, { Name = "${var.identifier}-subnet-group" })
}

# ── RDS instance ─────────────────────────────────────────────────────────────
resource "aws_db_instance" "main" {
  identifier             = var.identifier   # e.g. "payment-api-dev", "payment-api-prod"
  engine                 = "postgres"
  engine_version         = var.engine_version
  instance_class         = var.instance_class
  allocated_storage      = var.allocated_storage
  max_allocated_storage  = var.max_allocated_storage
  db_name                = var.db_name
  username               = var.username
  password               = var.password
  multi_az               = var.multi_az
  backup_retention_period = var.backup_retention_period
  db_subnet_group_name   = aws_db_subnet_group.main.name
  vpc_security_group_ids = [aws_security_group.rds.id]
  storage_encrypted      = true
  deletion_protection    = true
  skip_final_snapshot    = false
  final_snapshot_identifier = "${var.identifier}-final-snapshot"

  tags = merge(var.tags, {
    Name        = var.identifier
    Environment = split("-", var.identifier)[length(split("-", var.identifier)) - 1]
  })
}

# ── Outputs ───────────────────────────────────────────────────────────────────
output "endpoint"          { value = aws_db_instance.main.endpoint }
output "port"              { value = aws_db_instance.main.port }
output "db_name"           { value = aws_db_instance.main.db_name }
output "security_group_id" { value = aws_security_group.rds.id }

Note on the Environment tag: rather than adding a separate environment variable to the module interface, the environment is derived from the last segment of the identifier (e.g. payment-api-dev → dev). This avoids duplicating information — the identifier already encodes the environment. If your naming convention differs, add an explicit environment variable to the module interface instead.

deletion_protection = true and skip_final_snapshot = false are set unconditionally for all environments. These are not prod-only — a deleted dev database with no snapshot can still cause hours of recovery work if a developer was testing against real data.

Generate scripts/bootstrap-state.sh — the one-time script to create the S3 bucket and DynamoDB table. Requirements: versioning enabled on the bucket, server-side encryption, public access blocked, DynamoDB table with LockID as the partition key, idempotent (safe to run if resources already exist), and output a clear summary of what was created.

Claude Code

This is the expected chicken-and-egg problem with remote state backends: Terraform cannot initialise the backend until the backend resources exist, but you cannot use Terraform to create those resources because the backend is not yet initialised. The bootstrap script solves this by creating the prerequisites with the AWS CLI directly.

scripts/bootstrap-state.sh (turn 4)
#!/usr/bin/env bash
# scripts/bootstrap-state.sh
# One-time setup: creates the S3 bucket and DynamoDB table required
# for Terraform remote state. Run once per AWS account before first terraform init.
# Idempotent — safe to re-run if resources already exist.
set -euo pipefail

readonly BUCKET="sourcefuse-tf-state"
readonly REGION="ap-south-1"
readonly LOCK_TABLE="terraform-state-lock"

log() { echo "[$(date -u +%H:%M:%S)] $*"; }

# ── S3 Bucket ─────────────────────────────────────────────────────────────
if aws s3api head-bucket --bucket "$BUCKET" --region "$REGION" 2>/dev/null; then
  log "S3 bucket '$BUCKET' already exists — skipping creation"
else
  log "Creating S3 bucket '$BUCKET' in $REGION..."
  aws s3api create-bucket \
    --bucket "$BUCKET" \
    --region "$REGION" \
    --create-bucket-configuration LocationConstraint="$REGION"

  aws s3api put-bucket-versioning \
    --bucket "$BUCKET" \
    --versioning-configuration Status=Enabled

  aws s3api put-bucket-encryption \
    --bucket "$BUCKET" \
    --server-side-encryption-configuration \
    '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'

  aws s3api put-public-access-block \
    --bucket "$BUCKET" \
    --public-access-block-configuration \
    "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true"

  log "S3 bucket created with versioning, encryption, and public access blocked"
fi

# ── DynamoDB Table ────────────────────────────────────────────────────────
if aws dynamodb describe-table --table-name "$LOCK_TABLE" --region "$REGION" 2>/dev/null; then
  log "DynamoDB table '$LOCK_TABLE' already exists — skipping creation"
else
  log "Creating DynamoDB table '$LOCK_TABLE'..."
  aws dynamodb create-table \
    --table-name "$LOCK_TABLE" \
    --region "$REGION" \
    --attribute-definitions AttributeName=LockID,AttributeType=S \
    --key-schema AttributeName=LockID,KeyType=HASH \
    --billing-mode PAY_PER_REQUEST

  aws dynamodb wait table-exists \
    --table-name "$LOCK_TABLE" \
    --region "$REGION"

  log "DynamoDB table created with PAY_PER_REQUEST billing"
fi

# ── Summary ────────────────────────────────────────────────────────────────
echo ""
echo "Bootstrap complete. Next steps:"
echo "  terraform init -backend-config=\"key=payment-api/dev/terraform.tfstate\""
echo "  terraform plan -var-file=environments/dev.tfvars"
echo "  terraform apply -var-file=environments/dev.tfvars"

On PAY_PER_REQUEST billing for the lock table: state lock operations are infrequent — one acquire and one release per Terraform run. Provisioned capacity would require setting a read/write capacity unit estimate that is always too high for this workload. PAY_PER_REQUEST costs fractions of a cent per month for a typical team's apply frequency.

Turn 5 of 5 — Security review: prevent_destroy and prod-specific lifecycle
Engineer → Claude Code

Security review flagged two gaps in the module:

1. No prevent_destroy lifecycle rule — a terraform destroy on prod would execute without any barrier.
2. The module applies the same lifecycle rules to dev and prod. Dev should allow destroy freely; prod must prevent it.

The module cannot conditionally apply lifecycle rules based on a variable — Terraform does not allow dynamic lifecycle blocks. How do you handle this correctly? Show only the changes needed.

Claude Code

You're right that Terraform does not support dynamic lifecycle blocks — the lifecycle meta-argument cannot reference variables or locals. This is a known constraint. The correct pattern for environment-differentiated lifecycle rules is to use two separate resource definitions with a count or module-level conditional — but for RDS, the cleanest solution is to expose a boolean variable and use it to control deletion_protection, which achieves the same effect through an AWS-level guard rather than a Terraform-level one.

Add to modules/rds/variables.tf:

modules/rds/variables.tf — add this variable
variable "enable_deletion_protection" {
  type        = bool
  description = "Whether to enable RDS deletion protection. Set true for prod, false for dev/staging."
  default     = true   # Defaults to protected — must explicitly opt out
}

Update in modules/rds/main.tf — the aws_db_instance resource:

modules/rds/main.tf — update deletion_protection line
# Change from hardcoded:
  deletion_protection = true
# To variable-controlled:
  deletion_protection = var.enable_deletion_protection

Add to each environment file:

environments/dev.tfvars and staging.tfvars — add this line
enable_deletion_protection = false   # Allow destroy in non-prod environments
environments/prod.tfvars — add this line
enable_deletion_protection = true    # Prod: RDS API rejects deletion requests

Why this is better than prevent_destroy: prevent_destroy is a Terraform client-side guard — it stops terraform destroy from running, but only if it is present in the configuration at the time of the destroy. If someone removes the lifecycle block and then runs destroy, there is no barrier. deletion_protection = true is an AWS API-level guard — RDS will reject the deletion request regardless of what the Terraform configuration says. It requires a separate API call to disable, which is an intentional friction point that makes accidental deletion harder.

Step 5 of 5
Watch out

Claude Code produced a correct multi-environment structure across five turns, including a nuanced answer on Terraform lifecycle limitations. Here is what still requires environment-specific verification.

What Claude Code handled well
Backend key injected at init time rather than hardcoded, idempotent bootstrap script with AWS CLI existence checks, PAY_PER_REQUEST billing rationale for the lock table, all 15 variables explicitly set in every .tfvars file (no implicit defaults), correct explanation of why dynamic lifecycle blocks are not possible in Terraform and the API-level alternative (deletion_protection) that is more robust than prevent_destroy, environment identifier encoded in resource names for cost allocation.
  • Verify
    S3 bucket name must be globally unique. sourcefuse-tf-state is used throughout this example. S3 bucket names are globally unique across all AWS accounts. If this name is already taken, the bootstrap script will fail at the create-bucket step. Use a name that incorporates your AWS account ID or organisation prefix to guarantee uniqueness: e.g. sourcefuse-tf-state-{account-id}.
  • Verify
    The CI pipeline needs environment selection logic. The Example 5 pipeline deploys to EKS but does not yet select a Terraform environment. The pipeline's deploy job will need to inject the correct -backend-config key and -var-file path based on the target environment — typically derived from the branch name or a pipeline variable. This is a pipeline extension, not a Terraform change.
  • Verify
    Passwords must not be in .tfvars files in version control. The password values in all three .tfvars files use REPLACE_WITH_SECRET_MANAGER_VALUE placeholders. In practice, passwords should be injected at plan time from AWS Secrets Manager or SSM Parameter Store via a data source — not stored in the .tfvars file and not passed as a -var flag (which appears in shell history). If your .tfvars files are committed to version control, the password field must reference a data source, not a literal value.
  • Verify
    Disabling deletion_protection before destroy requires a separate apply. If you need to destroy a non-prod environment, you cannot run terraform destroy directly if deletion_protection = true is still in the state. First apply with enable_deletion_protection = false, wait for the RDS instance to update, then run terraform destroy. This two-step requirement is a feature, not a bug — it prevents accidental single-command destruction.
  • Note
    The environment tag is derived from the identifier, not a separate variable. The module extracts the environment from the last segment of var.identifier using split("-", var.identifier). This works for the naming convention payment-api-{env} but will produce incorrect tags if the identifier format changes. If your team uses a different naming convention, add an explicit environment variable to the module interface rather than deriving it.
Prompting tip for multi-environment IaC
The most important prompt addition for Terraform multi-environment work is explicitly naming the interface contract between files — in Turn 2, specifying "the module's variable interface is the variables.tf from Example 2 — use all those variables exactly as defined" produced a correctly wired module on the first pass. Without that constraint, Claude Code would have generated a plausible-but-different interface that would not accept the .tfvars values without modification. In multi-file Terraform, the variable interface is the integration contract — name it explicitly in every relevant prompt.
