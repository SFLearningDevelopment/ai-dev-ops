Step 1 of 5
The problem

The payment-api deployment (introduced in Example 5) needs to be made operationally complete. The current deployment manifest handles the basic workload spec — replicas, probes, security context — but it has no autoscaling, no disruption budget, and no way for the cluster to distribute pods safely across availability zones. During a recent node maintenance window, all three replicas landed on the same node being drained, causing a complete service outage for four minutes.

The task is to produce a full Kubernetes workload spec: the deployment (updated from Example 5), a Horizontal Pod Autoscaler, a PodDisruptionBudget, and a Service. Together these four manifests define not just how the application runs but how it scales, how it tolerates disruption, and how traffic reaches it.

Requirements
— Deployment: extend Example 5's manifest — add topology spread constraints to distribute pods across AZs, add topologySpreadConstraints, retain all existing security context and probe config
— HPA: scale between 3 and 10 replicas based on CPU (70%) and memory (80%) utilisation
— PDB: minimum 2 pods available at all times — node drains must not reduce available replicas below 2
— Service: ClusterIP service exposing port 3000, selector aligned to deployment labels
— All four manifests in a single k8s/ directory, applicable with kubectl apply -f k8s/
— Metrics server must be present in the cluster for HPA to function — document this dependency

k8s/hpa.yaml Horizontal Pod Autoscaler — CPU and memory based scaling, 3–10 replicas Scaling

Step 2 of 5
The naive approach

The naive Kubernetes workload for a production service is often just a Deployment and a Service — the minimum that makes the application reachable. HPA and PDB are added "later when needed." The four-minute outage during node maintenance is what "later" looks like.

k8s/deployment.yaml (naive — from Example 5, no topology constraints)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      # No topologySpreadConstraints — all pods may schedule on one node
      containers:
        - name: payment-api
          image: REGISTRY/payment-api:latest
          # ... probes, resources, securityContext from Example 5 ...
k8s/ directory — what is missing
k8s/
├── deployment.yaml    # Present — but no topology constraints
└── (nothing else)

# Missing:
# hpa.yaml    — no autoscaling; traffic spikes cause pod crashes or 503s
# pdb.yaml    — no disruption budget; node drain can take all pods offline
# service.yaml — no service; traffic routing depends on ad-hoc port-forward

Four distinct operational gaps — each one a production incident waiting to happen:

  • Availability
    No topology spread constraints. Kubernetes schedules pods on available nodes without any affinity or spread rules. Under normal conditions, all three replicas may land on the same node. When that node is drained for maintenance, a rolling eviction removes all pods simultaneously — exactly what caused the four-minute outage. Three replicas on three nodes is not guaranteed without topologySpreadConstraints.
  • Availability
    No PodDisruptionBudget. Without a PDB, Kubernetes permits draining a node by evicting every pod on it simultaneously, regardless of how many replicas are available. A PDB with minAvailable: 2 prevents any drain from proceeding if it would reduce available replicas below 2 — the drain blocks until a replacement pod is scheduled and ready on another node.
  • Scalability
    No Horizontal Pod Autoscaler. The deployment is pinned at 3 replicas regardless of load. A payment processing spike that doubles CPU usage will not trigger additional pods — it will degrade response times and eventually cause pod crashes due to resource limit exhaustion. The HPA from this example was the reason the previous Dockerfile had memory limits set to 512Mi (later found to be too low in Example 5).
  • Connectivity
    No Service manifest. Without a Service object, traffic reaches pods only via kubectl port-forward or direct pod IP. Pod IPs change on every restart. Any other service in the cluster that needs to call payment-api has no stable DNS name to target. The Service manifest is the Kubernetes-native mechanism for stable internal DNS and load balancing across pod replicas.
The core problem
A Deployment alone describes how an application runs. A complete workload spec describes how it runs, how it scales, how it tolerates disruption, and how it is reached. The gap between the two is invisible in normal operations and catastrophic during the first node maintenance window, traffic spike, or cluster upgrade.

Turn 1 of 5 — Deployment updated with topology spread constraints
Engineer → Claude Code

Update the deployment from Example 5 to add topology spread constraints. Requirements:

— Spread pods across availability zones using the topology.kubernetes.io/zone label
— Also spread across nodes using kubernetes.io/hostname
— whenUnsatisfiable: DoNotSchedule — hard constraint, do not schedule pods that would violate spread
— maxSkew: 1 for both constraints
— Retain all existing config from Example 5 (security context, probes, resources, emptyDir volume)

Claude Code
k8s/deployment.yaml (turn 1 — topology spread added)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payment
  labels:
    app: payment-api
    app.kubernetes.io/name: payment-api
    app.kubernetes.io/managed-by: ci
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      # ── Topology spread ──────────────────────────────────────────────────
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: payment-api
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: payment-api
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
      containers:
        - name: payment-api
          image: REGISTRY/payment-api:latest
          ports:
            - containerPort: 3000
          resources:
            requests:
              memory: 256Mi
              cpu: 250m
            limits:
              memory: 768Mi   # Increased from 512Mi — OOMKilled in Example 5
              cpu: 500m
          securityContext:
            readOnlyRootFilesystem: true
            allowPrivilegeEscalation: false
            capabilities:
              drop: [ ALL ]
          livenessProbe:
            httpGet:
              path: /health
              port: 3000
            initialDelaySeconds: 15
            periodSeconds: 20
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /health
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 10
            failureThreshold: 3
          volumeMounts:
            - name: logs
              mountPath: /app/logs
      volumes:
        - name: logs
          emptyDir: {}

Two notes on DoNotSchedule: this is a hard constraint — if the cluster does not have enough nodes across the required zones to satisfy maxSkew: 1, the scheduler will leave pods in Pending state rather than violating the spread. If you have a 3-replica deployment and only 2 AZs, the constraint can be satisfied (2 in one AZ, 1 in another, skew = 1). If you have fewer nodes than replicas, pods will be pending — which is preferable to silently concentrating all replicas on one node.

Also updated: memory limit raised from 512Mi to 768Mi to address the OOMKilled root cause from Example 5, Turn 4.

Turn 2 of 5 — HPA with CPU and memory metrics
Engineer → Claude Code

Generate k8s/hpa.yaml. Requirements:

— Target: payment-api Deployment in payment namespace
— Min replicas: 3 (matches Deployment spec), max: 10
— Scale up on average CPU utilisation > 70%
— Scale up on average memory utilisation > 80%
— Use autoscaling/v2 API (not v1 — v1 only supports CPU)
— Scale-down stabilisation: 5 minutes (prevent thrashing after a traffic spike)

Claude Code
k8s/hpa.yaml (turn 2)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: payment-api
  namespace: payment
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment-api   # Must match deployment name exactly
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # 5 minutes — prevents thrashing
      policies:
        - type: Pods
          value: 1
          periodSeconds: 60   # Remove at most 1 pod per minute on scale-down
    scaleUp:
      stabilizationWindowSeconds: 0     # Scale up immediately — no delay on traffic spike
      policies:
        - type: Pods
          value: 2
          periodSeconds: 60   # Add at most 2 pods per minute on scale-up

On the asymmetric scale-up/scale-down behaviour: scale-up is immediate with no stabilisation window because a payment service under load needs new pods quickly. Scale-down has a 5-minute stabilisation window because a brief traffic dip after a spike should not immediately remove pods that may be needed again in the next minute. The 1-pod-per-minute scale-down rate prevents a large fleet from collapsing too quickly after a sustained traffic reduction.

Prerequisite: HPA resource metrics require the Kubernetes metrics-server to be installed in the cluster. Without it, kubectl get hpa will show <unknown> for current metrics and the HPA will not scale. Verify with: kubectl top pods -n payment — if this returns data, metrics-server is installed and functioning.

Turn 3 of 5 — PodDisruptionBudget
Engineer → Claude Code

Generate k8s/pdb.yaml. Minimum 2 pods must be available at all times. The PDB must account for the fact that HPA may scale the deployment up to 10 replicas — at 10 replicas, the PDB should still allow some disruption, not block all node drains. Explain the minAvailable vs maxUnavailable choice.

Claude Code
k8s/pdb.yaml (turn 3)
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-api
  namespace: payment
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: payment-api

minAvailable: 2 vs maxUnavailable: 1 — why minAvailable is correct here:

maxUnavailable: 1 means at most 1 pod may be unavailable at any time. At 3 replicas this is equivalent to minAvailable: 2. But at 10 replicas (HPA maximum), maxUnavailable: 1 still allows only 1 pod to be drained at a time — making node maintenance very slow when the deployment is scaled up under load.

minAvailable: 2 is an absolute floor regardless of the current replica count. At 3 replicas it prevents draining below 2. At 10 replicas it allows 8 pods to be evicted simultaneously — node maintenance proceeds quickly during high-traffic periods. This is the correct production behaviour: protect a meaningful minimum while not over-constraining operational work at scale.

Important: if minReplicas on the HPA is ever reduced below 2, the PDB will block all node drains entirely — the HPA could scale down to 2 pods, and the PDB's minAvailable: 2 means zero evictions are permitted. Keep minReplicas ≥ minAvailable + 1 as an operational rule.

Claude Code

The metrics-server is not installed. The error the server could not find the requested resource (get pods.metrics.k8s.io) confirms that the metrics.k8s.io API is not registered — which means the metrics-server component is missing from the cluster. kubectl top pods failing confirms this independently.

Install metrics-server using the official manifest:

Install metrics-server
# Standard installation — works on most clusters
kubectl apply -f \
  https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# Verify installation (may take 60–90 seconds to become ready)
kubectl rollout status deployment/metrics-server -n kube-system
kubectl top nodes   # Should return CPU and memory data

If your cluster uses self-signed TLS certificates (common on EKS with private API endpoints): the standard metrics-server manifest will fail with a TLS verification error. In that case, patch the deployment to skip TLS verification:

Metrics-server with TLS skip (EKS private endpoint)
kubectl patch deployment metrics-server -n kube-system \
  --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-",
        "value":"--kubelet-insecure-tls"}]'

After metrics-server is ready, wait 2–3 minutes for the HPA controller to collect initial metrics. The <unknown> values will resolve and scaling will become active.

Label alignment audit — all four manifests:

Label alignment check
# deployment.yaml — pod template labels
spec.template.metadata.labels.app: payment-api  ✓

# service.yaml — selector
spec.selector.app: payment-api                   ✓ matches Deployment pod labels

# hpa.yaml — scaleTargetRef

spec.scaleTargetRef.kind: Deployment              ✓

# Result: all five label/name references are aligned.
# If any of these drift — e.g. if the Deployment is renamed — the following

# PDB protects nothing, topology spread applies to no pods.

All references are consistent. The label app: payment-api is the single coordination point across all four manifests. Renaming the deployment without updating all four selectors simultaneously will cause silent failures — traffic is not routed, autoscaling does not apply, and the PDB does not protect any pods.

The refined output

Four manifests, each addressing a different operational concern. The diff below shows what changed in the Deployment from Example 5, and the file connection diagram maps how the four manifests coordinate.

Deployment: Example 5 → Example 7
# No topology constraints — all pods may land on one node topologySpreadConstraints: - maxSkew: 1 topologyKey: topology.kubernetes.io/zone whenUnsatisfiable: DoNotSchedule labelSelector: { matchLabels: { app: payment-api } } - maxSkew: 1 topologyKey: kubernetes.io/hostname whenUnsatisfiable: DoNotSchedule labelSelector: { matchLabels: { app: payment-api } } memory limit: 512Mi # OOMKilled in Example 5 memory limit: 768Mi # 150% of observed peak usage
How the four manifests coordinate
deployment.yaml →
Source of truth for the pod template and labels. The label app: payment-api on the pod template is the single value that all other manifests reference. Topology spread constraints are evaluated by the scheduler at pod creation time — pods are placed on nodes/zones that keep skew ≤ 1.
hpa.yaml →
References the Deployment by name via scaleTargetRef. The HPA controller reads CPU and memory metrics from the metrics-server, compares them to the targets, and adjusts the Deployment's spec.replicas field accordingly. The Deployment then schedules new pods within the constraints defined by the topology spread rules.
pdb.yaml →
Selects pods via label selector — independent of replica count. The PDB controller intercepts eviction requests (from node drains, cluster upgrades, or manual evictions). It permits eviction only if the result would leave at least 2 pods available. This applies regardless of whether the HPA has scaled to 3 or 10 replicas.
service.yaml →
Routes traffic to all pods matching app: payment-api. The Service maintains its endpoint list dynamically — as the HPA adds or removes pods, the Service endpoint list updates automatically. The ClusterIP provides a stable internal DNS name (payment-api.payment.svc.cluster.local) that other services use regardless of how many pods are running.

Step 5 of 5
Watch out

Claude Code produced four correctly structured manifests with sound reasoning on the HPA behaviour design and PDB constraint choice. Here is what your specific cluster environment must still verify.

What Claude Code handled well
Asymmetric HPA scale-up/scale-down behaviour with rationale, correct minAvailable vs maxUnavailable choice for HPA-managed deployments with explanation of the interaction, DoNotSchedule topology spread as a hard constraint explained correctly, metrics-server prerequisite flagged in Turn 2 before the failure in Turn 4, Turn 4 TLS patch for EKS private endpoint clusters included without prompting, label alignment audit across all five reference points in Turn 5, memory limit corrected to address the Example 5 OOMKilled root cause.
  • Verify
    Topology spread with DoNotSchedule requires enough nodes across zones. With 3 replicas and a maxSkew: 1 zone constraint, the cluster needs nodes in at least 2 zones. With 10 replicas (HPA maximum), at least 2 zones are needed and at least 10 schedulable nodes. If zone capacity is insufficient during a traffic spike, the HPA will attempt to create pods and they will remain in Pending state rather than violating the spread — which is correct behaviour but requires monitoring for pending pods as a capacity signal.
  • Verify
    HPA memory metrics require memory requests to be set. The HPA calculates memory utilisation as current / request. If resources.requests.memory is not set in the Deployment, memory utilisation will always show as 0% and the memory metric will never trigger scaling. The Deployment in this example has requests.memory: 256Mi — verify this is present and accurate for your service's actual idle consumption.
  • Verify
    The PDB minReplicas ≥ minAvailable + 1 rule must be maintained operationally. If the HPA minReplicas is ever reduced to 2 and the PDB minAvailable stays at 2, all node drains will be blocked indefinitely. This is a configuration relationship that Kubernetes does not validate — there is no admission webhook that prevents this misconfiguration. Add a comment to both manifests noting the dependency, and include a check in your runbook for any HPA minimum replica changes.
  • Verify
    Node labels must be present for topology spread to work. The zone constraint uses topology.kubernetes.io/zone. Most managed Kubernetes services (EKS, GKE, AKS) apply this label automatically. Self-managed clusters may not. Verify with: kubectl get nodes --show-labels | grep topology.kubernetes.io/zone. If the label is absent, the zone spread constraint will be silently ignored — pods will schedule without zone awareness.
  • Note
    The Service DNS name follows a predictable pattern. Once the Service is applied, other services in the cluster can reach payment-api at payment-api.payment.svc.cluster.local:3000 — or simply payment-api.payment:3000 from within the same cluster. Services in the same namespace can use just payment-api:3000. This stable DNS name is independent of pod restarts, scaling events, and rolling updates — it is the primary reason to define a Service rather than using pod IPs directly.
Prompting tip for Kubernetes workload specs
The most effective addition to any Kubernetes prompt is naming the operational scenario you are guarding against. In Turn 1, specifying "all replicas landed on one node during a node drain" produced topology spread constraints with DoNotSchedule — the hard constraint appropriate for a payment service. A prompt that only says "spread pods across zones" would likely have produced ScheduleAnyway — the soft constraint that merely attempts spread without enforcing it. The failure mode makes the constraint choice unambiguous.
🔍 Reviewer question — E7-1
In Example 7, the PDB used `minAvailable: 2` rather than `maxUnavailable: 1`. Why does this choice matter when the HPA scales the deployment to 10 replicas?
AAt 10 replicas, `maxUnavailable: 1` would allow 9 pods to be evicted simultaneously
BAt 10 replicas, `maxUnavailable: 1` would still only allow 1 pod to be evicted at a time, making node drains very slow; `minAvailable: 2` allows 8 simultaneous evictions
CAt 10 replicas, `minAvailable: 2` prevents the HPA from scaling below 2 replicas
D`maxUnavailable: 1` is not supported by Kubernetes when HPA is enabled
`maxUnavailable: 1` means at most 1 pod may be unavailable at any time — regardless of how many replicas are running. At 10 replicas, this serialises node drains one pod at a time. `minAvailable: 2` is an absolute floor: at 10 replicas, 8 pods can be evicted simultaneously. Node maintenance proceeds much faster during high-traffic periods.
