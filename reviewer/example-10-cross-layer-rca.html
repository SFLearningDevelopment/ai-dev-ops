Step 1 of 5
The problem
Tier 3 — what changes
Tiers 1 and 2 were about generating artifacts — Dockerfiles, pipelines, manifests, scripts. Tier 3 is about diagnosing systems. The engineer's job shifts from "write this" to "tell me what is wrong and why." Claude Code's job shifts from code generator to cross-layer analyst. The interaction structure changes accordingly: Turn 1 is not a generation prompt — it is an evidence dump. The value Claude Code provides is not in the code it writes but in the causal chain it constructs from evidence that spans multiple system layers simultaneously.

A production deployment of payment-api completed successfully — the CI/CD pipeline from Example 5 reported green, the Argo CD sync from Example 8 showed Healthy, and the smoke test from Example 9 passed. Twenty minutes later, the on-call engineer receives a PagerDuty alert: payment success rate has dropped from 99.4% to 61%. No code was changed. The deployment is the only recent change.

The engineer has four evidence sources. Each one alone is inconclusive. Together they point to a single root cause — but only if the evidence is read across layers simultaneously, not sequentially.

The Tier 3 shift in prompting
In Tier 1 and 2, prompts were structured as requirements lists. In Tier 3, the primary prompt is an evidence dump — the engineer pastes raw signals from multiple system layers and asks Claude Code to correlate them. The quality of the diagnosis depends on the completeness and accuracy of the evidence, not on the precision of the requirements. This is a fundamentally different prompting mode and the examples are designed to make that shift visible.

Step 2 of 5
The naive approach

The naive approach to a production incident is to investigate one layer at a time, in the order that feels most natural — usually starting with application logs, then moving to Kubernetes, then to infrastructure if the first two layers don't explain it. This sequential investigation misses cross-layer causality.

The naive investigation sequence
Step 1: Check application logs → sees connection refused → concludes "database is down" → checks RDS → RDS is running → confused.

Step 2: Check Kubernetes → sees OOMKilled → concludes "memory limit too low" → increases memory limit → redeploys → problem persists.

Step 3: Check RDS metrics → sees DatabaseConnections at 100% → concludes "connection pool leak" → restarts pods → brief improvement, then problem returns.

Step 4: Escalates. Someone notices the Terraform apply ran at the same time as the deployment. Someone else checks the parameter group diff. The root cause is found 90 minutes after the incident started.

Each step in the naive sequence is individually rational. The problem is that sequential single-layer investigation treats symptoms as causes. The OOMKilled event is a consequence of connection exhaustion (pods holding open connections until killed). The connection refused errors are a consequence of max_connections being halved. The root cause — the parameter group change — is only visible when the Terraform state diff is correlated with the RDS CloudWatch metrics.

  • Methodology
    Sequential layer investigation misses causal chains that span layers. Each layer makes sense in isolation. The application logs show connection errors — the database appears to be rejecting connections. The Kubernetes events show OOMKilled — memory appears to be the problem. Neither observation is wrong; both are symptoms of the same root cause at a different layer. Sequential investigation cannot distinguish cause from consequence without explicit cross-layer correlation.
  • Methodology
    The highest-signal evidence (Terraform state diff) is checked last. In most incident investigations, infrastructure change history is consulted only after application and cluster signals have failed to explain the problem. But in this scenario, the Terraform apply is the causal event — everything else flows from it. The investigation pattern that checks infrastructure changes first, in correlation with the application signals, reaches the root cause in one step rather than four.

Step 3 of 5
The Claude Code interaction

Five turns. Turn 1 is the evidence dump — all four layers provided simultaneously. Turn 2 asks for the causal chain. Turn 3 asks for immediate mitigation steps. Turn 4 asks for a permanent fix. Turn 5 asks for a prevention rule to add to the Terraform module.

Why all four layers in Turn 1
The defining characteristic of Tier 3 prompting is providing cross-layer evidence in the first turn, not sequentially across turns. Providing evidence one layer at a time forces Claude Code to reason about each layer independently before seeing the connections — the same mistake as the naive sequential investigation. Providing all layers simultaneously lets Claude Code read the signals as a system and identify the causal chain on the first pass.

What is the root cause?

Claude Code

Root cause: the Terraform apply halved max_connections on the RDS parameter group from 200 to 100, while the application's connection pool is sized at 50 connections per pod with 3 replicas — 150 total connections required, exceeding the new limit of 100.

The causal chain across all four layers:

Causal chain — root cause to symptoms
# Infrastructure layer (root cause)
Terraform apply: max_connections 200 → 100
RDS rejects new connections above limit 100

# Application layer (first-order consequence)
Pool: size=50 × 3 replicas = 150 connections needed
RDS accepts only 100 → 50 connections refused
connection pool exhausted → pending=23 → payment failures

# Kubernetes layer (second-order consequence)
Pods hold open connections waiting for pool slots
Pending connections accumulate → heap grows → OOMKilled
OOMKilled pod restarts → new pod requests 50 connections
→ exceeds limit again → cycle repeats

# Smoke test (false negative)
/health → 200 (process is alive)
/ready  → 503 (database unavailable)
Smoke test passed /health but /ready was 503 at 14:23:01
→ The deployment was already degraded when smoke test ran

The OOMKilled event is a consequence, not a cause — pods are holding pending connection attempts in memory until the kernel kills them. Increasing the memory limit would not fix the problem; it would only delay the kill. The /ready: 503 in the application log at 14:23:01 is particularly significant: the smoke test from Example 9 checks both /health and /ready, but if it ran before 14:23:01 it may have caught the service in a window where /ready was still returning 200 before the connection pool fully exhausted.

Turn 2 of 5 — Immediate mitigation
Engineer → Claude Code

Confirmed. The parameter group change was unintentional — it was in a PR that was meant to only update the deployment image tag. What do I do right now to restore service?

Claude Code

Two parallel tracks — do both simultaneously:

Track 1: Restore max_connections immediately (fastest path)

Immediate mitigation — restore max_connections via AWS CLI
# Restore max_connections to 200 without waiting for a Terraform apply
aws rds modify-db-parameter-group \
  --db-parameter-group-name payment-api-prod \
  --parameters "ParameterName=max_connections,ParameterValue=200,ApplyMethod=immediate"

# Verify the change was applied
aws rds describe-db-parameters \
  --db-parameter-group-name payment-api-prod \
  --query "Parameters[?ParameterName=='max_connections']"

# Watch DatabaseConnections metric recover
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name DatabaseConnections \
  --period 60 --statistics Average \
  --start-time $(date -u -d '5 minutes ago' +%Y-%m-%dT%H:%M:%SZ) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ)

Track 2: Restart pods to clear accumulated connection backlog

Restart pods after parameter group change
# Rolling restart — respects PDB from Example 7 (minAvailable: 2)
kubectl rollout restart deployment/payment-api -n payment

# Watch recovery
kubectl rollout status deployment/payment-api -n payment --timeout=180s

The ApplyMethod=immediate flag applies the parameter change without requiring a DB reboot — max_connections is a dynamic parameter in PostgreSQL. New connections will be accepted as soon as the parameter propagates (typically under 60 seconds). The pod restart clears the accumulated pending connection state so the pool re-establishes cleanly against the restored limit.

Turn 3 of 5 — Permanent fix: separate infrastructure and application changes
Engineer → Claude Code

Service is recovering. Now — how do I prevent this from happening again? The PR that caused this was supposed to be a deployment-only change. The Terraform parameter group change was in the same PR by mistake.

Claude Code

Three structural changes — each one addresses a different failure mode in the chain:

Fix 1: Separate CI/CD pipelines for infrastructure and application changes.

The root architectural problem is that a single PR could contain both a Terraform change and a Kubernetes deployment change. These have different blast radii, different rollback mechanisms, and different approval requirements. Add a path filter to the pipeline from Example 5:

.github/workflows/cicd.yml — add path filters
on:
  push:
    branches: [ main ]
    paths:
      - 'k8s/**'
      - 'Dockerfile'
      - 'src/**'
      # Explicitly exclude infra/ — a change there should trigger a separate workflow

# Separate workflow: .github/workflows/infra.yml
on:
  push:
    paths:
      - 'infra/**'

Fix 2: Add a connection budget validation to the Terraform RDS module.

The module from Example 6 should validate that max_connections is at least twice the application's connection pool size. Add to modules/rds/variables.tf:

modules/rds/variables.tf — add connection budget guard
variable "max_connections" {
  type        = number
  description = "PostgreSQL max_connections parameter. Must be >= 2x the application connection pool size."
  default     = 200

  validation {
    condition     = var.max_connections >= 100
    error_message = "max_connections must be >= 100. Application pool is 50 per replica × 3 replicas minimum."
  }
}

Fix 3: Add max_connections to the smoke test verification.

The smoke test from Example 9 checks /health and /ready. Add a connection pool check to the readiness probe itself in the application — or add a dedicated /metrics check to the smoke test that verifies the connection pool is not exhausted before the deployment is marked successful.

Turn 5 of 5 — Prevention rule added to Terraform module
Engineer → Claude Code

Add a lifecycle rule to the RDS parameter group resource in the module that prevents any change to max_connections from being applied without explicit approval — similar to how we handle deletion_protection in Example 6. Should this be a Terraform prevent_destroy, an external approval gate, or something else?

Claude Code

Neither prevent_destroy nor a lifecycle rule is the right mechanism here. prevent_destroy prevents the resource from being deleted, not changed. There is no Terraform-native lifecycle rule that blocks specific parameter changes — lifecycle rules only control create/destroy behaviour, not field-level updates.

The correct mechanism is a combination of two things:

1. Separate the parameter group from the main RDS module apply. Move the parameter group into its own Terraform resource with a separate state key, so it cannot be changed in the same apply as anything else. Changes to it require a dedicated plan and apply cycle with explicit review:

infra/rds-params/main.tf — isolated parameter group
# Separate state from the main RDS module.
# Any change here requires: terraform plan -target=aws_db_parameter_group.payment_api
# followed by explicit approval before apply.
resource "aws_db_parameter_group" "payment_api" {
  name   = "payment-api-${var.environment}"
  family = "postgres15"

  parameter {
    name         = "max_connections"
    value        = var.max_connections
    apply_method = "immediate"
  }

  lifecycle {
    # Changing the parameter group family requires replacement — prevent accidental destroy
    prevent_destroy = true
  }
}

2. Add a pre-plan check in CI that flags max_connections changes.

.github/workflows/infra.yml — flag max_connections changes
- name: Check for max_connections changes
  run: |
    if terraform plan -out=tfplan && terraform show -json tfplan | \
      jq -e '.resource_changes[] | select(.change.actions[] == "update") |
        select(.change.before.parameter[].value != .change.after.parameter[].value) |
        select(.change.before.parameter[].name == "max_connections")' > /dev/null; then
      echo "::warning::max_connections is changing in this plan. Review connection budget before applying."
      echo "Application pool: 50 connections/pod × 3 replicas minimum = 150 connections required"
    fi

This CI check does not block the plan — it emits a warning annotation on the PR that the reviewer must acknowledge. Blocking the apply on a warning creates friction for legitimate changes; a visible warning with documented context creates friction only for unreviewed changes.

Step 4 of 5
The refined output

Tier 3 examples do not produce a primary code artifact — they produce a diagnosis, a set of targeted fixes, and a prevention rule. The refined output is the causal chain and the structural changes that prevent recurrence.

Root cause chain — infrastructure to symptoms
Infrastructure →
Terraform apply reduces max_connections from 200 to 100. This is the causal event. It is in the same PR as the deployment image update — neither the engineer nor the reviewer noticed it because the deployment change was the intended focus of the PR review.
Application →
Connection pool exhausted. The application has a pool of 50 connections per pod, 3 replicas = 150 total. RDS now accepts only 100. The 50 excess connections are refused. The pool fills to capacity, then requests queue as pending. Payment transactions fail when the queue timeout is reached.
Kubernetes →
OOMKilled is a second-order consequence. Pods accumulate in-memory connection state for pending requests. Heap grows. Memory limit (768Mi from Example 7) is reached. Kernel kills the pod. New pod starts — requests 50 connections — exceeds limit again — cycle repeats. Increasing the memory limit would delay but not prevent the kill cycle.
Detection gap →
Smoke test passed during a 3-minute false window. The smoke test ran at 14:05, before connection pool exhaustion. /health returned 200 (process alive), /ready returned 200 (pool not yet full). By 14:10, /ready was returning 503. The deployment was already degraded before the detection signal fired. This gap motivates the connection pool health check addition to the smoke test.

Three structural fixes resulted from the RCA, each closing a different gap:

  • Prevention
    Path-filtered CI/CD pipelines prevent infrastructure and application changes from being deployed in a single pipeline run. The blast radius of each change type is now scoped independently.
  • Prevention
    Connection budget validation in the Terraform module catches max_connections values that are below the application's minimum at plan time, before the change reaches the cluster.
  • Prevention
    Connection pool health check in the smoke test closes the 3-minute detection gap by verifying that the connection pool has capacity before marking the deployment successful.

Step 5 of 5
Watch out

Claude Code produced a correct cross-layer RCA from a single evidence dump, correct immediate mitigation steps, and structurally sound prevention rules. Here is what it cannot verify without your specific environment.

What Claude Code handled well
Cross-layer causal chain identified from simultaneous evidence in Turn 1 (not sequential), OOMKilled correctly identified as a consequence not a cause, smoke test detection gap identified from the 14:23:01 log line, ApplyMethod=immediate specified correctly for a dynamic PostgreSQL parameter, prevent_destroy correctly rejected for field-level change prevention with the correct alternative explanation, connection budget arithmetic (50 × 3 = 150 > 100) derived from evidence without being stated explicitly.
  • Verify
    max_connections is dynamic in PostgreSQL but not in all RDS engine versions. The mitigation uses ApplyMethod=immediate, which works for dynamic parameters. In PostgreSQL on RDS, max_connections is static by default — it requires a DB reboot to take effect. Verify with: aws rds describe-db-parameters --db-parameter-group-name payment-api-prod --query "Parameters[?ParameterName=='max_connections'].IsModifiable". If the parameter requires a reboot, ApplyMethod=pending-reboot is required and the connection limit will not be restored until the RDS instance restarts.
  • Verify
    The connection pool size assumption (50 per pod) must be verified. Claude Code derived 50 connections per pod from the log line Pool size 50, active 50, idle 0, pending 23. This is the runtime pool size — but the configured pool size (in the application's database configuration) may differ from the runtime observation, particularly if the pool had not yet reached its configured maximum. Check the application's DATABASE_POOL_SIZE or equivalent environment variable before using 50 as the baseline for the connection budget validation.
  • Verify
    The CI check's jq filter for max_connections changes is approximate. The jq expression in Turn 5 filters parameter group changes by comparing before/after values for parameters named max_connections. The exact JSON structure of terraform show -json output varies between Terraform versions and provider releases. Validate the filter against a test plan output before relying on it in CI.
  • Note
    This incident demonstrates the value of cross-layer evidence in Turn 1. The diagnosis was complete in a single turn because all four evidence layers were provided simultaneously. Had the engineer provided only the application logs first, the initial hypothesis would have been "database is down" — which is incorrect. The Terraform state diff is the evidence that converts an incorrect hypothesis into a correct root cause. In real incidents, the temptation is to provide evidence as it is gathered — this example is designed to counter that instinct.
Prompting tip for cross-layer RCA
Provide all evidence layers in the first turn, not sequentially. Sequential evidence provision mirrors sequential investigation — it forces Claude Code to form and then revise hypotheses one layer at a time, which is the same mistake as the naive investigation approach. A single evidence dump with all layers simultaneously lets Claude Code read the signals as a connected system. The richer the evidence in Turn 1, the more precise the diagnosis — sparse evidence produces hedged hypotheses; complete evidence produces confident causal chains.
