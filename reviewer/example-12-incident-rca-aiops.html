Step 1 of 5
The problem
Module bridge
This example is the explicit handoff point between Module 1 (DevOps automation) and Module 2 (AIOps use cases). The first three turns follow the Tier 3 pattern established in Examples 10 and 11 — cross-layer evidence, causal chain diagnosis, targeted remediation. Turns 4 and 5 introduce something new: Claude Code's triage output is structured as a machine-readable AIOps payload that can be consumed by remediation automation, alert enrichment pipelines, and runbook generation systems. This structured handoff is what connects DevOps diagnosis to AIOps action.

At 02:14 UTC, PagerDuty fires a P1 alert: payment-api error rate has spiked to 34% and p99 latency has exceeded 8 seconds. The on-call engineer is paged. By the time they open their laptop, three other alerts have fired: a pod restart count alert, a network policy alert, and a certificate expiry warning.

Four alerts in 90 seconds, two of which look unrelated. The engineer's first job is to determine which alerts describe the same incident and which are coincidental. Their second job is to produce a structured triage summary that can feed into the AIOps remediation pipeline — not just fix the immediate problem, but produce output that makes the next similar incident faster to resolve.

Step 2 of 5
The naive approach

The naive approach to a multi-alert incident is to treat each alert independently and work through them in priority order. This produces correct remediations for each alert but misses the causal relationships between them — wasting time and producing a postmortem that lists symptoms rather than root causes.

The naive alert-by-alert investigation
Alert 1 (error rate): Engineer checks app logs → sees TLS errors → assumes network issue → checks network policy → policy is fine → confused. Checks if payment processor is down → processor is up. Escalates to networking team.

Alert 2 (pod restarts): Different engineer checks pod events → sees liveness probe failures → assumes app bug in the new deployment → checks deployment history → no recent deployment → confused. Checks memory limits → fine. Restarts pods → error rate briefly drops then returns.

Alert 3 (network policy): Third engineer checks network policy → no changes → dismisses as noise. Closes alert.

Alert 4 (cert expiry): Someone eventually opens the cert expiry warning that fired at 02:15 → sees payment processor client cert expired at 02:00 → this is the root cause. Time elapsed: 47 minutes.
  • Methodology
    Alert-by-alert investigation treats symptoms as independent incidents. The pod restarts are caused by the liveness probe failing because the error rate is high. The error rate is high because TLS calls are failing. The TLS calls are failing because the client cert expired. All four alerts describe the same causal chain — but investigated independently, they look like four separate problems.
  • Methodology
    No structured handoff to remediation automation. Even after finding the root cause, the postmortem is written in prose, the cert rotation process is manual, and the next expiry will produce the same 47-minute investigation. An AIOps handoff converts the triage output into a structured payload that can trigger automated cert rotation, update the monitoring system with the causal chain for future alert correlation, and seed the runbook with the diagnosis steps.

Which alerts are related? What is the root cause?

Claude Code

Three of the four alerts describe the same incident. One is noise.

Root cause: the payment-processor-client TLS certificate expired at 02:00 UTC. The cert rotation job failed silently on 2026-03-14 — one day before expiry — and the failure was not alerted. When the cert expired, every outbound TLS handshake to the payment processor API failed with x509: certificate has expired. The application's liveness probe monitors error rate; at 34% error rate, the probe threshold was exceeded, triggering pod restarts.

Alert correlation:

Alert correlation analysis
02:14:03  P1  error rate > 5%          → CAUSAL (cert expired → TLS failures → error rate)
02:14:31  P2  pod restart count > 2    → CAUSAL (error rate → liveness probe → restart)
02:14:47  P3  network policy change    → NOISE  (no policy change; scanner false positive)
02:15:02  P2  certificate expiry       → ROOT CAUSE (cert expired 14 minutes earlier)

Causal chain: cert expired (02:00) → TLS failures (02:00) → error rate spike (02:00–02:14)
              → liveness threshold exceeded (02:14) → pod restarts (02:14) → three alerts (02:14–02:15)

The network policy alert is a false positive — the scanner classifies cert expiry events
as policy-adjacent and fires the alert. No policy changed. Dismiss immediately.

Why the rotation job failure was not caught: the cert-rotation-cronjob failed on 2026-03-14 — one day before expiry — but no alert fired for the job failure. Kubernetes CronJob failures do not fire alerts by default; the failure was visible in the job status but no monitoring rule covered it. The 14-minute gap between cert expiry (02:00) and the first alert (02:14) is the liveness probe evaluation window — the probe fires after the error rate sustained above threshold for 4 minutes, then the alert fires after 10 minutes of pod restarts.

Turn 2 of 5 — Immediate remediation
Engineer → Claude Code

Confirmed. What do I do right now to restore service?

Claude Code

Two steps in sequence — cert renewal first, then pod restart:

Immediate remediation sequence
# Step 1: Renew the expired client certificate
# The exact command depends on your cert issuer (Let's Encrypt, internal CA, etc.)
# For cert-manager (most common Kubernetes cert management tool):
kubectl annotate certificate payment-processor-client \
  -n payment \
  cert-manager.io/issuer-kind=ClusterIssuer \
  --overwrite

# Force cert-manager to reissue immediately:
kubectl delete certificaterequest \
  -n payment \
  -l cert-manager.io/certificate-name=payment-processor-client

# Watch for new cert to be issued (typically 30–60 seconds):
kubectl get certificate payment-processor-client -n payment -w

# Step 2: Restart pods to pick up the new cert
# Wait until certificate shows Ready=True before restarting
kubectl rollout restart deployment/payment-api -n payment
kubectl rollout status deployment/payment-api -n payment --timeout=180s

# Verify recovery:
kubectl logs -l app=payment-api -n payment --tail=20 | grep -E "ERROR|payment-processor"
# Should show no new TLS errors after pod restart

If your certificates are not managed by cert-manager: the renewal process depends on your CA. The pattern is the same — renew the client cert, store it in the Kubernetes Secret that the pod mounts, then restart pods. Check that the secret payment-processor-client-cert (or equivalent) is updated with the new cert before restarting pods — restarting without renewing first will not fix the issue.

Turn 3 of 5 — CronJob failure alerting (the missed detection)
Engineer → Claude Code

Service is recovering. The rotation job failed the day before expiry and nobody was alerted. How do I add alerting for CronJob failures so this cannot happen silently again?

Claude Code

Two complementary alerting approaches — both are needed because they cover different failure modes:

Kubernetes CronJob failure alert (PrometheusRule)
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: cronjob-failure-alerts
  namespace: payment
spec:
  groups:
    - name: cronjob.rules
      rules:
        - alert: CronJobFailed
          expr: |
            kube_job_status_failed{namespace="payment"} > 0
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "CronJob {{ $labels.job_name }} failed in namespace {{ $labels.namespace }}"
            description: "Job {{ $labels.job_name }} has failed. Check: kubectl describe job {{ $labels.job_name }} -n {{ $labels.namespace }}"

        - alert: CertificateExpiringSoon
          expr: |
            certmanager_certificate_expiration_timestamp_seconds
              - time() < 7 * 24 * 3600
          for: 1h
          labels:
            severity: critical
          annotations:
            summary: "Certificate {{ $labels.name }} expires in less than 7 days"
            description: "Certificate {{ $labels.name }} in namespace {{ $labels.namespace }} expires at {{ $value | humanizeTimestamp }}. Rotation job: cert-rotation-cronjob"

The two rules cover complementary failure modes: CronJobFailed catches the rotation job failing (what happened here), and CertificateExpiringSoon catches the cert approaching expiry regardless of why the rotation job failed (defense in depth). Both should be alerting — the job failure should have fired 24 hours before expiry; the cert expiry alert should have fired 7 days before. Neither was in place.

Turn 5 of 5 — Cert rotation pipeline hardening
Engineer → Claude Code

The rotation job ran on a CronJob but failed silently. What is the right pattern for a cert rotation job that (a) alerts on failure, (b) verifies the new cert is valid before the old one expires, and (c) emits a structured event that the AIOps pipeline can consume?

Claude Code

Three design requirements, each addressed separately:

(a) Alert on failure: already covered in Turn 3 via the CronJobFailed PrometheusRule. In addition, add successfulJobsHistoryLimit: 3 and failedJobsHistoryLimit: 3 to the CronJob spec so job history is retained for debugging.

(b) Verify new cert before old one expires:

cert-rotation-job.sh — verification before cutover
#!/usr/bin/env bash
set -euo pipefail

log() { echo "[$(date -u +%H:%M:%S)] $*"; }

CERT_NAME="payment-processor-client"
NAMESPACE="payment"
MIN_VALIDITY_DAYS=14   # New cert must be valid for at least 14 days

# Trigger renewal
log "Triggering renewal for $CERT_NAME"
kubectl delete certificaterequest \
  -n "$NAMESPACE" \
  -l cert-manager.io/certificate-name="$CERT_NAME" \
  --ignore-not-found

# Wait for new cert to be issued (max 5 minutes)
kubectl wait certificate "$CERT_NAME" \
  -n "$NAMESPACE" \
  --for=condition=Ready \
  --timeout=300s

# Verify new cert is valid for at least MIN_VALIDITY_DAYS
EXPIRY=$(kubectl get secret "${CERT_NAME}-tls" -n "$NAMESPACE" \
  -o jsonpath='{.data.tls\.crt}' | base64 -d | \
  openssl x509 -noout -enddate | cut -d= -f2)

EXPIRY_EPOCH=$(date -d "$EXPIRY" +%s)
NOW_EPOCH=$(date +%s)
DAYS_REMAINING=$(( (EXPIRY_EPOCH - NOW_EPOCH) / 86400 ))

if [[ "$DAYS_REMAINING" -lt "$MIN_VALIDITY_DAYS" ]]; then
  log "ERROR: New cert only valid for $DAYS_REMAINING days (minimum: $MIN_VALIDITY_DAYS)" >&2
  exit 1
fi

log "Cert renewed successfully. Valid for $DAYS_REMAINING days (expires: $EXPIRY)"

# (c) Emit structured event for AIOps pipeline
kubectl create event \
  --namespace "$NAMESPACE" \
  --field-manager=cert-rotation \
  "cert-rotated-$(date +%s)" \
  --type=Normal \
  --reason=CertificateRotated \
  --message="$(jq -n \
    --arg cert "$CERT_NAME" \
    --arg expiry "$EXPIRY" \
    --argjson days "$DAYS_REMAINING" \
    '{event:"certificate_rotated", cert:$cert, new_expiry:$expiry, days_remaining:$days}')"

The structured Kubernetes event in step (c) is machine-readable — the AIOps pipeline can watch for CertificateRotated events in the payment namespace and use them to update the certificate inventory, confirm remediation of active cert-expiry alerts, and reset the detection window for future expiry monitoring.

Step 5 of 5
Watch out

Claude Code correctly identified the root cause, dismissed the noise alert, produced a sequenced remediation with a prerequisite gate, and generated a structured AIOps payload. Here is what your environment must verify.

What Claude Code handled well
Noise alert correctly identified and dismissed in Turn 1 from the network policy audit evidence, causal chain positions assigned correctly enabling downstream alert suppression, prerequisite gate on the rolling restart (certificate_ready must be satisfied before pod restart — otherwise the restart does not fix the problem), human_review_required: false correctly set given confidence 0.97 on all correlations, structured Kubernetes event from the rotation job enabling machine-readable confirmation of remediation.
  • Verify
    The cert renewal commands assume cert-manager. The remediation in Turn 2 uses cert-manager CRDs (Certificate, CertificateRequest). If your cluster uses a different certificate management system — HashiCorp Vault PKI, AWS Certificate Manager, or a custom cert rotation script — the renewal commands will differ. The pattern (trigger renewal → wait for ready → restart pods) is correct regardless of the tool; the specific commands depend on your cert management implementation.
  • Verify
    The AIOps payload schema must match your pipeline's expected format. The JSON structure in Turn 4 is designed to be illustrative rather than tied to a specific AIOps platform. Before feeding this payload into a remediation pipeline, verify that the field names, confidence score format, and action schema match what your pipeline expects. The causal_chain_position and prerequisite fields in particular may need to be translated to your platform's schema.
  • Verify
    The human_review_required: false flag should be conservative in production. A confidence score of 0.97 is high — but for a payment service, automated remediation without human review should be reserved for well-understood, low-risk actions (renewing a cert, restarting pods). For more invasive actions (scaling down, modifying network policy, changing resource limits), set human_review_required: true regardless of confidence score. The threshold for automated action should be a policy decision, not a confidence calculation.
  • Note
    This example is the bridge to Module 2. The AIOps handoff payload in Turn 4 is the form in which Module 2's use cases begin. Module 2 (AIOps use cases) covers incident analysis, RCA, and remediation patterns — all of which consume structured triage payloads as input. The payload format introduced here, the alert correlation schema, and the remediation action structure with prerequisite gates are all patterns that Module 2 builds on.
Prompting tip for multi-alert incidents
Include all concurrent alerts in the first turn — not just the highest-priority one. The noise alert (PD-003, network policy change) was dismissed in Turn 1 because its evidence (the network policy audit log) was provided alongside the other signals. Without that evidence, the network policy alert would have been a plausible hypothesis requiring its own investigation thread. Providing all concurrent alerts with their supporting evidence simultaneously lets Claude Code correlate and dismiss noise in a single pass — the same principle as the simultaneous evidence dump in Examples 10 and 11, applied specifically to alert triage.
