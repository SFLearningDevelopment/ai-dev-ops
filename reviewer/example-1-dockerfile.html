Dockerfile for a Node.js API service

Tier 1 — Single-file task Containerisation 3-turn interaction DevOps automation
1
Step 1 of 5
The problem

You have a Node.js Express API service — payment-api — that runs fine locally and passes all tests. The service needs to be containerised so it can be deployed to an EKS cluster via an existing CI/CD pipeline. The pipeline expects an image pushed to ECR, built from a Dockerfile in the repo root.

The team is small, the deadline is today, and no one has containerised a Node.js service for this repo before. There is no existing Dockerfile to reference.

Context you have
The service runs on Node 20. It listens on port 3000. It has a /health endpoint that returns 200 OK. Dependencies are in package.json. There is no build step — it runs node src/index.js directly. The ECR repo and EKS namespace are already provisioned.

This is about as common a scenario as exists in DevOps. The question is not whether you can write a Dockerfile — it's whether the one you write under time pressure will be production-worthy, or whether it will accumulate security and performance debt that surfaces six months later.

Step 2 of 5
The naive approach

Under time pressure, most engineers reach for a Dockerfile they've used before — or copy one from a tutorial. Here is what typically gets written, and what gets committed to the repo:

Dockerfile (naive) dockerfile 
FROM node:latest

WORKDIR /app

COPY . .

RUN npm install

EXPOSE 3000

CMD ["node", "src/index.js"]

It works. The image builds, the container runs, the CI pipeline goes green. But this Dockerfile carries six distinct problems that will surface in production or security review:

  • Security
    Runs as root. The container process has UID 0 inside the container. If the application is compromised, the attacker has root access to the container filesystem and any mounted volumes. Every security benchmark flags this.
  • Security
    node:latest is unpinned and bloated. latest resolves to a different image on every build — your prod image and your dev image may differ. The full node image includes compilers, package managers, and hundreds of packages that have no business being in a production container. Attack surface is proportional to image size.
  • Performance
    Layer cache always misses on npm install. COPY . . copies everything — including src/ — before npm install. Any change to any source file invalidates the layer cache and forces a full reinstall of all dependencies. On a large node_modules, this adds 2–4 minutes to every build.
  • Correctness
    No .dockerignore. Without it, COPY . . copies node_modules/, .git/, .env files, test fixtures, and local build artifacts into the image. node_modules alone can add hundreds of megabytes and the wrong platform binaries.
  • Operations
    No HEALTHCHECK. Docker and Kubernetes cannot distinguish between a container that is running and one that is running but unhealthy. Without a health check, a crashed-but-running process will not trigger a restart until a liveness probe is separately configured — if one is configured at all.
  • Correctness
    Installs dev dependencies. npm install without --omit=dev includes testing frameworks, type checkers, linters, and build tools in the production image. These add size and expose tools that serve no purpose at runtime.
The core problem
None of these issues cause an immediate failure. The service runs. The tests pass. The CI pipeline is green. This is exactly why naive Dockerfiles persist in codebases for years — they only become problems at the worst possible time: a security audit, a production incident, or a compliance review.

Step 3 of 5
The Claude Code interaction

This interaction runs three turns. Notice what changes at each turn and why — the engineer is not just accepting output, they are feeding back specific real results and asking for targeted refinements. That discipline is what makes the difference between a first-pass Dockerfile and a production-grade one.

Turn 1 of 3 — Initial generation with context
Engineer → Claude Code

I need a production-grade Dockerfile for a Node.js Express API service called payment-api. Here is the context:

— Node version: 20
— Entrypoint: node src/index.js
— Port: 3000
— Health endpoint: GET /health returns 200
— No build step, no TypeScript compilation
— npm install --omit=dev for production deps only

Requirements:
— Must not run as root
— Layer cache must not be invalidated by source file changes
— Image must be as small as reasonably possible without distroless
— Must include a HEALTHCHECK
— Include a .dockerignore alongside it

The image will be pushed to AWS ECR and run on EKS. No shell access is needed in the final image.

Claude Code

Here is a production-grade Dockerfile and accompanying .dockerignore for payment-api.

Dockerfile (turn 1 output) 
FROM node:20-alpine AS base

# Install dumb-init for proper signal handling
RUN apk add --no-cache dumb-init

# Create a non-root user
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

WORKDIR /app

# Copy dependency manifests first — layer cache preserved on source changes
COPY package.json package-lock.json ./

# Install production dependencies only
RUN npm ci --omit=dev && npm cache clean --force

# Copy source after deps — cache hit on reinstall if only src changed
COPY src/ ./src/

# Set ownership before switching user
RUN chown -R appuser:appgroup /app

USER appuser

EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD wget -qO- http://localhost:3000/health || exit 1

ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "src/index.js"]

Key decisions made:

— node:20-alpine rather than node:20: Alpine reduces the image from ~1.1 GB to ~180 MB while retaining everything a pure-Node service needs. I avoided distroless per your constraint — Alpine still gives you a shell for debugging if needed.

— dumb-init: Node does not handle SIGTERM gracefully when run as PID 1. Without an init process, Kubernetes sends SIGTERM and the container keeps running until the grace period expires and it receives SIGKILL. dumb-init correctly forwards signals and reaps zombie processes.

— npm ci instead of npm install: npm ci installs exactly what is in package-lock.json, fails on any discrepancy, and is significantly faster in CI environments.

— Layer ordering: package.json and package-lock.json are copied and installed before src/ is copied. This means changing any source file does not invalidate the dependency install layer.

Turn 2 of 3 — Build output and one real issue

The engineer builds the image locally. It succeeds but produces a warning, and a quick Trivy scan flags one issue. Both get pasted back verbatim.

Engineer → Claude Code

Build succeeded. Two things to address:

1. Build warning (verbatim):

docker build output
1 warning found (use docker --debug to expand):
- JSONArgsRecommended: JSON arguments recommended for CMD to prevent
  unintended behavior related to OS signals (line 20)
  More info: https://docs.docker.com/go/dockerfile/rule/json-args-recommended/

2. Trivy scan finding (verbatim):

trivy image scan
HIGH: CVE-2024-4067 in micromatch 4.0.5
Package: micromatch
Installed Version: 4.0.5
Fixed Version: 4.0.8
Severity: HIGH
Description: Regular Expression Denial of Service (ReDoS)
Layer: node_modules/micromatch

Please address both. For the CVE — micromatch is a transitive dependency. I don't control its version directly from my package.json.

Claude Code

Warning fix: The CMD line in turn 1 already uses JSON array form. The warning is likely about the HEALTHCHECK CMD, which used shell form. Here is the corrected healthcheck line:

Dockerfile — corrected HEALTHCHECK
# Shell form (flagged by linter):
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD wget -qO- http://localhost:3000/health || exit 1

# JSON form (correct):
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD ["wget", "-q", "--spider", "http://localhost:3000/health"]

CVE fix: For transitive dependency CVEs you don't control directly, the correct approach in npm is an overrides block in package.json. Add this to your package.json:

package.json — add overrides block
{
  "overrides": {
    "micromatch": "^4.0.8"
  }
}

After adding this, run npm install locally to regenerate package-lock.json, commit both files, then rebuild the image. The Trivy finding will clear. This is the correct production pattern for transitive CVEs — do not pin the entire dependency tree, only the affected package via overrides.

Note: if micromatch is only used by dev tooling (e.g. Jest, ESLint), it will not appear in the production image at all since we use --omit=dev. Run npm ls micromatch --omit=dev to confirm whether it's actually in the production dependency graph before adding the override.

Turn 3 of 3 — Final hardening

The engineer confirmed micromatch is dev-only (the Trivy finding disappears after rebuilding with --omit=dev). One more requirement surfaces: the security team mandates a read-only root filesystem for all EKS workloads.

Engineer → Claude Code

micromatch confirmed dev-only — not in the final image, Trivy is clean. Build is good.

One more requirement: our security policy mandates readOnlyRootFilesystem: true in the Kubernetes SecurityContext for all workloads. When I apply that, the container crashes on startup with:

kubectl logs payment-api-xxx
Error: EACCES: permission denied, open '/app/logs/app.log'
    at Object.openSync (node:fs:596:3)
    at Object.writeFileSync (node:fs:2278:35)
    at createLogger (/app/src/logger.js:12:5)

The app writes logs to /app/logs/. With a read-only root filesystem, that write fails. I cannot change the app's logging path right now.

Claude Code

The correct solution is to mount a writable emptyDir volume at /app/logs in the Kubernetes deployment manifest — not to relax the readOnlyRootFilesystem constraint. The Dockerfile itself does not change; the write permission comes from Kubernetes.

Add this to your deployment spec:

deployment.yaml — volumes and mounts
containers:
  - name: payment-api
    securityContext:
      readOnlyRootFilesystem: true
      runAsNonRoot: true
      runAsUser: 1000
      allowPrivilegeEscalation: false
    volumeMounts:
      - name: logs
        mountPath: /app/logs
volumes:
  - name: logs
    emptyDir: {}

emptyDir is ephemeral — it lives for the lifetime of the pod and is wiped on restart. This is intentional: container logs should be shipped to a logging backend (CloudWatch, Loki, Datadog) by a sidecar or node-level agent, not persisted to the container filesystem. The emptyDir mount satisfies the app's write requirement while keeping the root filesystem read-only.

Also note: runAsUser: 1000 in the SecurityContext must match the UID of appuser created in the Dockerfile. Verify with docker run --rm payment-api id — it should confirm UID 1000. If the Alpine adduser command assigned a different UID, align the SecurityContext accordingly.

Step 4 of 5
The refined output

Here is the final Dockerfile after all three turns. Each decision is annotated so the next engineer who touches this file understands the intent — not just the implementation.

Dockerfile (final) 
# ── Base image ──────────────────────────────────────────────────────────────
# node:20-alpine chosen over node:20 (full Debian): ~180 MB vs ~1.1 GB.
# Alpine provides enough tooling for a pure-Node service.
# Pin to a specific minor for reproducibility; update intentionally.
FROM node:20-alpine

# ── Init process ────────────────────────────────────────────────────────────
# Node does not handle SIGTERM correctly as PID 1.
# dumb-init forwards signals and reaps zombie processes.
# Required for graceful pod shutdown in Kubernetes.
RUN apk add --no-cache dumb-init

# ── Non-root user ───────────────────────────────────────────────────────────
# Mandated by CIS Docker Benchmark 4.1.
# UID/GID must match runAsUser in the Kubernetes SecurityContext.
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

WORKDIR /app

# ── Dependency layer (cache-optimised) ──────────────────────────────────────
# Copy manifests before source. This layer is only invalidated when
# package.json or package-lock.json changes — not on every source edit.
# npm ci: installs exactly package-lock.json, fails on drift, faster in CI.
COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force

# ── Source ──────────────────────────────────────────────────────────────────
# Copied after deps so source changes hit cache after the install layer.
COPY src/ ./src/

# ── Ownership ───────────────────────────────────────────────────────────────
RUN chown -R appuser:appgroup /app
USER appuser

EXPOSE 3000

# ── Health check ────────────────────────────────────────────────────────────
# JSON form required (shell form triggers linter warning CIS 4.6).
# start-period gives the app time to initialise before checks begin.
# wget used instead of curl — curl not installed in alpine base.
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD ["wget", "-q", "--spider", "http://localhost:3000/health"]

# ── Entrypoint ──────────────────────────────────────────────────────────────
ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "src/index.js"]

Step 5 of 5
Watch out

Claude Code produced a strong Dockerfile in three turns. Here are the things it got right, and the things you still need to verify yourself — because Claude Code cannot know your specific environment.

What Claude Code handled well
Layer ordering for cache efficiency, dumb-init for signal handling, npm ci over npm install, JSON-form HEALTHCHECK, non-root user, .dockerignore scope. These are patterns it applies correctly and consistently — you should not need to prompt for them explicitly on future Dockerfiles.
  • Verify
    UID alignment between Dockerfile and SecurityContext. Alpine's adduser assigns UIDs dynamically. The Dockerfile creates appuser but does not pin a specific UID. Verify the actual UID with docker run --rm payment-api id and ensure runAsUser in the Kubernetes SecurityContext matches exactly. A mismatch causes a runtime failure, not a build failure.
  • Verify
    Base image availability in your ECR mirror. If your EKS cluster pulls from a private ECR mirror rather than Docker Hub, node:20-alpine must exist in that mirror. Claude Code cannot know your registry topology. Verify before pushing to production. If the image is absent, the pod will fail with ImagePullBackOff.
  • Verify
    Pin the image tag before production. node:20-alpine is a floating tag — it will resolve to a different digest as Alpine and Node release patches. Pin to a specific digest (node:20-alpine@sha256:...) for fully reproducible production builds. Claude Code generated the correct tag family but did not pin the digest — that requires your CI pipeline to resolve and record it.
  • Verify
    emptyDir logs are ephemeral. The Turn 3 solution mounts /app/logs as an emptyDir. Logs written there are lost on pod restart. If log persistence matters — for audit trails or compliance — ensure a node-level log shipper (Fluentd, Fluent Bit) is capturing container stdout/stderr, and redirect the app's file logger to stdout instead of a file. This is an application change outside the Dockerfile scope.
  • Note
    No multi-stage build was used here. This service has no build step — node src/index.js runs directly. If you later add TypeScript compilation or a bundler, the Dockerfile will need a multi-stage build: a builder stage that compiles, and a runtime stage that copies only the compiled output. Claude Code handles multi-stage builds well — prompt for it explicitly when the build step arrives.
Prompting tip for future Dockerfiles
The Turn 1 prompt worked well because it was specific about constraints rather than intent. "Production-grade" alone is too vague. The effective additions were: explicit Node version, entrypoint command, port, health endpoint path, and the four named requirements (no root, cache-optimised, minimal image, healthcheck). Give Claude Code the same specificity for any new service and the first-pass output will be close to production-ready.
🔍 Reviewer question — E1-1
In Example 1, Claude Code added `dumb-init` to the Dockerfile without being asked. What operational problem does `dumb-init` solve?
AIt reduces the Docker image size by removing unnecessary OS packages
BIt ensures the Node.js process handles SIGTERM correctly when Kubernetes drains a pod
CIt prevents the container from running as root
DIt enables layer caching during the Docker build
A Node.js process running as PID 1 without an init system does not handle SIGTERM gracefully. When Kubernetes drains a pod, it sends SIGTERM — without dumb-init, the process ignores it and is forcibly killed. dumb-init acts as a minimal init system that forwards signals correctly.
