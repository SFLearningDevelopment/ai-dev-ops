Step 1 of 5
The problem

The payment-api team has accumulated twelve Prometheus alert rules over nine months. Each alert fires reliably — but when they fire at 03:00, the on-call engineer opens them to find a single line of metric context with no operational guidance. The alert says what crossed a threshold; it does not say why it matters, what to check first, or what the last three times this alert fired looked like.

The result is that every P2 and P3 incident begins with 10–20 minutes of context gathering that experienced engineers do from memory and junior engineers do by Slack-messaging the team at 03:00. This is the problem that alert enrichment and runbook generation solves — not by removing the alert, but by attaching structured operational context to it before it reaches the engineer.

What this example produces
Unlike Examples 10–12, which diagnosed existing incidents, Example 13 is proactive — it produces enrichment and runbooks for alerts that have not yet fired in the current context. The engineer provides the raw alert definitions, service context, and incident history; Claude Code produces enriched alert metadata and a structured runbook. The output is usable immediately as documentation, and machine-parseable as input to an AIOps alert management system.

Step 2 of 5
The naive approach

The naive alert definition is a threshold with a label. The naive runbook is a Confluence page that has not been updated since the alert was created.

Naive alert definition — no operational context
- alert: HighErrorRate
  expr: rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) > 0.05
  for: 2m
  labels:
    severity: critical
  annotations:
    summary: "High error rate on {{ $labels.service }}"
    # No description of what causes this alert
    # No links to dashboards or runbooks
    # No context about what 5% means for this service
    # No triage steps
    # No escalation path
The core problem
The on-call engineer receives a Slack notification at 03:00: "High error rate on payment-api." They open PagerDuty and find the alert expression. They open Grafana and look at a graph. They look at the logs. They remember what happened last time — if they were on-call last time. If they were not, they start from zero. The alert contains everything the monitoring system knows and nothing the engineering team knows. Alert enrichment closes that gap proactively, before the next 03:00 page.

Claude Code

Three observations from the incident history before producing the enrichment:

HighErrorRate has three distinct root cause categories across its three firings: external dependency failure (processor timeout), deployment regression, and infrastructure change (cert expiry). No single triage path covers all three. The runbook must branch early on distinguishing between these categories rather than prescribing a single investigation sequence.

PodMemoryPressure at 85% should trigger investigation immediately — two of the three historical firings were caused by bugs (memory leak, connection leak) that worsened over time. The one traffic-spike firing self-resolved via HPA. The enrichment should flag that 85% memory pressure is not a safe "wait and see" threshold for this service.

DatabaseConnectionPoolExhausted is causally linked to HighErrorRate — when the pool exhausts, payment transactions fail, which triggers HighErrorRate within minutes. The runbook for DatabaseConnectionPoolExhausted should reference the HighErrorRate alert as a likely co-firer and explicitly sequence: fix the pool issue before investigating the error rate. The two alerts are correlated at Example 10's root cause level.

Ready to produce enriched annotations and runbooks.

Engineer → Claude Code

Generate the full structured runbook for HighErrorRate. The runbook should branch on the three root cause categories from the incident history. Include the diagnostic commands, decision points, and resolution actions for each branch. It should be usable by an engineer who has never seen this service before.

Claude Code
Runbook: HighErrorRate — payment-api
# Runbook: HighErrorRate — payment-api
# Alert: 5xx error rate > 5% for 2+ minutes
# SLO impact: Payment success rate below 99.5%
# Typical duration: 8–35 minutes (3 historical firings)
# Last updated: auto-generated from incident history

## STEP 1: Check for co-firing alerts (30 seconds)
argocd # Not relevant here

# Is DatabaseConnectionPoolExhausted also firing?
kubectl get events -n payment --field-selector reason=OOMKilling --sort-by=.lastTimestamp
# If yes → go to BRANCH C (pool exhaustion). Fix pool before returning here.

## STEP 2: Check application logs (1 minute)
kubectl logs -l app=payment-api -n payment --tail=50 --since=5m | \
  grep -E "ERROR|payment-processor|x509|connection"

# Pattern A: "TLS handshake failed" or "x509: certificate" → BRANCH A (cert issue)
# Pattern B: "payment-processor: timeout" or "ECONNREFUSED" → BRANCH B (external API)
# Pattern C: "connection pool exhausted" or "pg-pool" → BRANCH C (DB pool)
# No clear pattern → STEP 3

## STEP 3: Check for recent deployment (1 minute)
kubectl rollout history deployment/payment-api -n payment | tail -5
# If deployment in last 2 hours → BRANCH D (deployment regression)
# If no recent deployment → STEP 4

## STEP 4: Check external dependency health (1 minute)
# Check payment-processor API status page (bookmark in team wiki)
curl -s https://status.payment-processor.com/api/v2/status.json | jq .status
# If degraded → BRANCH B (external API). No action from our side — monitor and wait.

────────────────────────────────────────────────────────────────
BRANCH A: TLS certificate issue
────────────────────────────────────────────────────────────────
# Identify which cert has expired
kubectl get certificates -n payment
# Look for status: False or NotReady

# Renew expired cert (cert-manager)
kubectl delete certificaterequest -n payment \
  -l cert-manager.io/certificate-name=<expired-cert-name>

# Wait for renewal, then restart pods
kubectl wait certificate <cert-name> -n payment --for=condition=Ready --timeout=300s
kubectl rollout restart deployment/payment-api -n payment
# See full procedure in Example 12 runbook

────────────────────────────────────────────────────────────────
BRANCH B: External payment processor API degraded
────────────────────────────────────────────────────────────────
# This is not recoverable from our side. Actions:
# 1. Confirm on status page (see STEP 4)
# 2. Enable payment-api degraded mode if implemented (returns 503 with retry-after)
# 3. Notify checkout-service team to surface user-facing message
# 4. Monitor processor status — alert will resolve when processor recovers
# 5. Do NOT restart pods — they will not fix an external dependency failure
# Typical resolution: 10–30 minutes (processor-side recovery)

────────────────────────────────────────────────────────────────
BRANCH C: Database connection pool exhausted
────────────────────────────────────────────────────────────────
# Follow DatabaseConnectionPoolExhausted runbook first.
# Return here after pool is recovered — HighErrorRate should auto-resolve.

────────────────────────────────────────────────────────────────
BRANCH D: Deployment regression
────────────────────────────────────────────────────────────────
# Roll back the deployment
kubectl rollout undo deployment/payment-api -n payment
kubectl rollout status deployment/payment-api -n payment --timeout=180s
# Verify error rate recovers in next 2–3 minutes
# File a bug report against the rolled-back version before marking resolved

The branching structure matches the three root cause categories from the incident history, with the most common pattern (external API) deprioritised in favour of the most time-sensitive check (co-firing pool alert) at Step 1. Branch B includes the explicit instruction "do NOT restart pods" — a common mistake when engineers assume restarting will fix any service degradation.

  • Value
    Historical pattern annotation encodes institutional memory into the alert. The three most common root causes, with their average resolution times, are now visible to any engineer who opens the alert — not just those who were on-call for the historical incidents. This is the primary value of alert enrichment: making experienced-engineer knowledge available at 03:00 to whoever is paged.
  • Value
    The do_not field prevents the most common mitigation mistake. Restarting pods when the root cause is an external API failure is the most common wrong action in a HighErrorRate incident. Encoding it as a machine-readable constraint lets the AIOps pipeline suppress automated restart actions when the diagnosis points to an external dependency — preventing an action that adds noise without fixing anything.
  • Value
    Alert correlation is bidirectional in the enrichment payload. HighErrorRate lists DatabaseConnectionPoolExhausted as a co-fire that should be resolved first. DatabaseConnectionPoolExhausted lists HighErrorRate as a downstream symptom to resolve automatically. Both relationships are in the payload — the AIOps pipeline can use either alert as the entry point and navigate to the correct resolution sequence regardless of which fires first.

Step 5 of 5
Watch out

Claude Code produced accurate enrichment grounded in the incident history, a correctly branched runbook, and a machine-readable payload with bidirectional correlation rules. Here is what requires ongoing maintenance and human judgment.

What Claude Code handled well
Identified that HighErrorRate has three distinct root cause categories requiring runbook branching rather than a single triage path, correctly deprioritised external API as the first check (check co-firing pool alert first — faster resolution), do_not: restart_pods_if_external_api_degraded derived from Branch B logic without prompting, bidirectional alert correlation (HighErrorRate ↔ DatabaseConnectionPoolExhausted) produced correctly, root cause probability distribution derived arithmetically from three historical firings per alert, PodMemoryPressure warning correctly flagged as not safe to "wait and see" despite being P2 severity.
  • Verify
    Root cause probabilities are based on three data points per alert. The probability distributions (e.g. 0.33/0.33/0.34 for HighErrorRate) are calculated from exactly three historical firings. Three firings is a statistically thin sample — the distributions will update significantly as more incidents accumulate. The enrichment payload should be regenerated every quarter, or after each new incident, to keep the distributions current. Treat the probabilities as rough priors, not reliable forecasts.
  • Verify
    The runbook assumes cert-manager for certificate operations. Branch A of the HighErrorRate runbook references cert-manager CRDs. If your certificate management uses a different system, this branch produces incorrect commands. The runbook structure (identify cert → renew → wait for ready → restart pods) is correct regardless of the tool; update the specific commands to match your implementation.
  • Verify
    Alert annotations have character limits in some notification systems. PagerDuty, Opsgenie, and other alerting tools may truncate annotation fields beyond a certain length. The historical_pattern and triage_first_step annotations are the longest — verify they render correctly in your notification system before deploying the PrometheusRule. If truncation occurs, shorten these fields or move the detail to the runbook URL.
  • Note
    Alert enrichment requires ongoing maintenance. The value of the historical pattern annotation degrades as new incidents occur that are not reflected in it. A runbook that references three incidents from six months ago and ignores the last five incidents is less useful than the unannotated alert. Establish a process to update alert annotations after each incident postmortem — or regenerate the enrichment payload automatically from your incident tracking system on a scheduled basis.
Prompting tip for alert enrichment
Provide incident history structured by alert, not by date. A chronological incident log ("here is everything that happened in Q1") requires Claude Code to categorise incidents by alert before it can derive root cause distributions — which adds a reasoning step that may introduce classification errors. Providing history pre-grouped by alert name ("here are the last three firings of HighErrorRate") lets Claude Code focus on deriving distributions and patterns rather than categorisation. The more structured the input, the more precise the enrichment output.
