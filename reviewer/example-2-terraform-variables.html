Terraform variables.tf with validation

Step 1 of 5
The problem

You are building a reusable Terraform module for provisioning an RDS PostgreSQL instance on AWS. The module will be used across three environments — dev, staging, and prod — by engineers who did not write it. The module needs a variables.tf that defines all inputs clearly, enforces sensible constraints, and makes it impossible to misconfigure the most common failure modes.

You have a list of inputs the module needs. The task is to turn that list into a variables.tf that is genuinely self-documenting, validates inputs at plan time rather than at apply time, and follows the conventions already established in the rest of the repo's modules.

Required inputs
identifier — unique name for the RDS instance
engine_version — PostgreSQL version (e.g. 15.4)
instance_class — RDS instance type (e.g. db.t3.medium)
allocated_storage — storage in GB
db_name — initial database name
username — master DB username
password — master DB password (sensitive)
vpc_id — VPC to place the instance in
subnet_ids — list of subnet IDs for the subnet group
allowed_cidr_blocks — CIDRs allowed to reach port 5432
multi_az — whether to enable Multi-AZ (default false)
backup_retention_period — days to retain automated backups
tags — map of tags applied to all resources

The module will be reviewed by the security team before it can be used in prod. Validation blocks that catch bad values at plan time — rather than letting Terraform apply partway and fail — are a hard requirement.

Step 2 of 5
The naive approach

The naive variables.tf is not dangerous the way a bad Dockerfile is dangerous — it won't get you breached. But it will cost you hours of debugging, produce confusing plan-time errors, and make the module brittle for anyone who isn't its author.

variables.tf (naive) hcl 
variable "identifier" {}

variable "engine_version" {}

variable "instance_class" {}

variable "allocated_storage" {}

variable "db_name" {}

variable "username" {}

variable "password" {}

variable "vpc_id" {}

variable "subnet_ids" {}

variable "allowed_cidr_blocks" {}

variable "multi_az" {
  default = false
}

variable "backup_retention_period" {
  default = 7
}

variable "tags" {
  default = {}
}

This looks complete — all 13 inputs are declared. But it has six distinct problems that will surface the moment someone other than the author uses the module:

  • Correctness
    No types anywhere. subnet_ids is declared as type any by default. An engineer passing a string instead of a list of strings will get a cryptic apply-time error from the AWS provider, not a clear plan-time message. Same for allowed_cidr_blocks, tags, and allocated_storage. Type constraints catch these instantly.
  • Security
    password is not marked sensitive. Without sensitive = true, the master DB password will appear in plain text in terraform plan output, CI logs, and state file diffs. Anyone with access to the CI pipeline history can read it.
  • Correctness
    No validation on allocated_storage. RDS requires a minimum of 20 GB. Passing 5 produces a confusing AWS API error at apply time — after the security group, subnet group, and parameter group have already been created. A validation block catches this at plan time, before any resources are touched.
  • Correctness
    No validation on backup_retention_period. AWS accepts 0–35 days. Passing 40 fails at apply time. Passing 0 silently disables backups — valid from AWS's perspective, but almost never the intent. A validation block can enforce a minimum of 1 for prod-grade modules.
  • Usability
    No descriptions. The next engineer using this module has to read main.tf to understand what identifier means, what format engine_version expects, or what allowed_cidr_blocks should contain. Descriptions appear in terraform-docs output and in IDE tooltips — they are the module's interface documentation.
  • Correctness
    No CIDR validation on allowed_cidr_blocks. Passing a malformed CIDR (a hostname, a bare IP without a prefix, a typo) fails at apply time inside the security group resource. A regex validation catches format errors at plan time with a human-readable error message instead of an AWS API exception.
The core problem
A variables.tf without types, descriptions, and validation is not a module interface — it's a list of names. It transfers all the cognitive load of "what does this accept and what are the constraints" from the module to every engineer who uses it. That cost compounds with every new caller.

The Claude Code interaction

Turn 1 of 3 — Typed, described, defaults set
Engineer → Claude Code

Generate a variables.tf for a reusable Terraform module that provisions an RDS PostgreSQL instance on AWS. Here are the inputs required:

identifier (string), engine_version (string), instance_class (string), allocated_storage (number, min 20), db_name (string), username (string), password (string, sensitive), vpc_id (string), subnet_ids (list of strings), allowed_cidr_blocks (list of strings, must be valid CIDRs), multi_az (bool, default false), backup_retention_period (number, default 7, range 1–35), tags (map of strings, default empty)

Requirements:
— Every variable must have a type constraint
— Every variable must have a description
— password must be marked sensitive
— Validation blocks for allocated_storage, backup_retention_period, and allowed_cidr_blocks
— Follow standard Terraform variable block style — no inline defaults mixed with complex blocks

Claude Code
variables.tf (turn 1 output) 
variable "identifier" {
  type        = string
  description = "Unique identifier for the RDS instance. Used as the resource name and in tags."
}

variable "engine_version" {
  type        = string
  description = "PostgreSQL engine version. Example: \"15.4\". Check AWS docs for supported versions."
}

variable "instance_class" {
  type        = string
  description = "RDS instance type. Example: \"db.t3.medium\". Must be a valid RDS instance class."
}

variable "allocated_storage" {
  type        = number
  description = "Storage allocated to the RDS instance in GB. Minimum 20."

  validation {
    condition     = var.allocated_storage >= 20
    error_message = "allocated_storage must be at least 20 GB. AWS RDS does not accept values below 20."
  }
}

variable "db_name" {
  type        = string
  description = "Name of the initial database created on the instance. Must be a valid PostgreSQL identifier."
}

variable "username" {
  type        = string
  description = "Master username for the RDS instance. Cannot be 'admin', 'root', or 'postgres' on Aurora."
}

variable "password" {
  type        = string
  sensitive   = true
  description = "Master password for the RDS instance. Marked sensitive — will not appear in plan output or logs."
}

variable "vpc_id" {
  type        = string
  description = "ID of the VPC in which the RDS instance and its subnet group will be created."
}

variable "subnet_ids" {
  type        = list(string)
  description = "List of subnet IDs for the DB subnet group. Must span at least two availability zones."
}

variable "allowed_cidr_blocks" {
  type        = list(string)
  description = "List of CIDR blocks permitted to reach port 5432. Example: [\"10.0.0.0/8\"]."

  validation {
    condition = alltrue([
      for cidr in var.allowed_cidr_blocks :
      can(regex("^([0-9]{1,3}\\.){3}[0-9]{1,3}/[0-9]{1,2}$", cidr))
    ])
    error_message = "All entries in allowed_cidr_blocks must be valid IPv4 CIDR notation (e.g. 10.0.0.0/8)."
  }
}

variable "multi_az" {
  type        = bool
  default     = false
  description = "Whether to deploy the RDS instance across multiple availability zones. Recommended true for prod."
}

variable "backup_retention_period" {
  type        = number
  default     = 7
  description = "Number of days to retain automated backups. Range: 1–35. Set to 0 disables backups (not recommended)."

  validation {
    condition     = var.backup_retention_period >= 1 && var.backup_retention_period <= 35
    error_message = "backup_retention_period must be between 1 and 35. AWS does not accept values outside this range."
  }
}

variable "tags" {
  type        = map(string)
  default     = {}
  description = "Map of tags applied to all resources created by this module."
}

Key decisions:

— sensitive = true on password suppresses it from all Terraform output, including state file diffs in CI. This does not encrypt the value in state — use a secrets manager reference in your root module instead of a plain string.

— The CIDR regex validates format only, not whether the CIDR is routeable or sensible. A value like 0.0.0.0/0 passes the regex but opens the database to the internet — semantic validation belongs in policy-as-code (OPA, Sentinel), not in variable validation blocks.

— backup_retention_period minimum is set to 1, not 0. Zero is valid from AWS's perspective but disables backups entirely. If you want to allow 0 as an intentional choice, remove the lower bound and add a comment.

Turn 2 of 3 — Security team requirement: storage autoscaling cap

The security team reviews the module and adds one requirement: max_allocated_storage must be declared, and if provided, must be greater than allocated_storage. This prevents the common mistake of setting a max lower than the initial allocation, which silently disables autoscaling.

Engineer → Claude Code

Security review added one requirement. Add a max_allocated_storage variable:

— Type: number
— Optional (default null — means autoscaling disabled)
— If provided, must be strictly greater than allocated_storage
— The cross-variable validation is the tricky part — max_allocated_storage can't reference allocated_storage directly in its own validation block in older Terraform versions. Handle this correctly.

Claude Code

You're right that cross-variable validation has a nuance. In Terraform ≥ 1.3, a validation block can reference other variables using var.* — but only variables that are already declared above it in the file. The safest pattern for cross-variable constraints is to put the validation on the variable that has the dependency, not the one being depended on.

Here is the new variable block. Add it after allocated_storage:

variables.tf — add after allocated_storage block 
variable "max_allocated_storage" {
  type        = number
  default     = null
  description = "Maximum storage limit in GB for RDS storage autoscaling. Set to null to disable autoscaling. If provided, must be greater than allocated_storage."

  validation {
    condition = (
      var.max_allocated_storage == null ||
      var.max_allocated_storage > var.allocated_storage
    )
    error_message = "max_allocated_storage must be greater than allocated_storage when autoscaling is enabled. Got max=${var.max_allocated_storage}, initial=${var.allocated_storage}."
  }
}

Why this works: the validation condition uses a short-circuit OR — if max_allocated_storage is null, the second clause is never evaluated and the validation passes. If it is set, Terraform checks that it exceeds allocated_storage. The error message includes both values so the engineer sees exactly what the conflict is, not just that a validation failed.

Note: this cross-variable reference in a validation block requires Terraform ≥ 1.3.0. If your team pins an older version, move this constraint into a precondition block on the aws_db_instance resource instead — it's semantically equivalent and supported from 1.2.0.

Step 4 of 5
The refined output

The Turn 3 output is the final file. Here is an annotated breakdown of the decisions that make it production-grade — the things that distinguish it from the naive version and justify each addition.

  • Type
    Every variable has an explicit type constraint. list(string) for subnet_ids and allowed_cidr_blocks, map(string) for tags, number for storage and retention, bool for multi_az. Type errors surface at terraform validate, before a single API call is made.
  • Security
    password marked sensitive = true. Terraform suppresses the value in all output, plan diffs, and log streams. Note: this does not encrypt the value in the state file. Manage the password via AWS Secrets Manager or SSM Parameter Store and pass a reference, not the literal string.
  • Validation
    Four validation blocks, each with a human-readable error message. allocated_storage ≥ 20, backup_retention_period between 1 and 35, CIDR format check on each entry in allowed_cidr_blocks, and the cross-variable guard on max_allocated_storage. All fire at plan time — before any resource is created or modified.
  • Convention
    Required variables before optional variables. Engineers reading the file see the mandatory inputs first. The section comments make the boundary explicit. Attribute ordering — type, description, sensitive, default, validation — is consistent throughout, matching the repo convention.
  • Note
    CIDR validation is format-only, not semantic. 0.0.0.0/0 passes the regex. Semantic validation — "is this CIDR too broad for a production database?" — belongs in Sentinel or OPA policy, not in a variable validation block. The description signals the intent; the policy enforces the constraint.

Step 5 of 5
Watch out

Claude Code handled the types, descriptions, validation blocks, and convention alignment correctly. Here are the things it cannot verify or get right without your specific context.

What Claude Code handled well
Full type coverage, sensitive flag, four validation blocks with human-readable error messages, cross-variable validation with null short-circuit, convention detection from the reference file (ordering, attribute sequence, description punctuation). All of this is replicable across any module with a well-specified prompt.
  • Verify
    Cross-variable validation requires Terraform ≥ 1.3. Claude Code flagged this correctly, but verify your required_version in versions.tf before merging. If your team pins ~> 1.2, the max_allocated_storage validation will fail silently or produce a confusing error at plan time. Move it to a precondition block on the aws_db_instance resource instead.
  • Verify
    sensitive = true does not secure the state file. The password is still stored in plain text in terraform.tfstate. If your state backend is S3, ensure the bucket has encryption at rest and access logging enabled. The better pattern is to pass an SSM Parameter Store or Secrets Manager ARN and have the module retrieve the value — but that requires changing the module's main.tf, not just variables.tf.
  • Verify
    CIDR validation is a format check, not a security check. 0.0.0.0/0 passes validation. If your security policy prohibits open CIDR ranges on database security groups — which it should — enforce this in Sentinel, OPA, or Checkov, not in the validation block. Claude Code correctly noted this, but it's worth verifying your policy tooling actually covers it.
  • Verify
    Convention alignment was inferred from one reference file. Claude Code detected four conventions from the VPC module. If other modules in the repo use a different ordering or description style, the output may not be fully aligned. Always run terraform-docs and compare with an existing module's rendered output before merging.
  • Note
    Variable validation blocks do not catch all AWS API constraints. For example, db_name must be a valid PostgreSQL identifier — no hyphens, no reserved words, max 63 characters. Claude Code did not add a validation block for this because the regex would be complex and the description signals the constraint. If your team wants hard enforcement, add a can(regex(...)) validation block for db_name explicitly.
Prompting tip for future variables.tf files
The Turn 3 pattern — sharing existing module files as convention references — is the highest-leverage input you can give Claude Code for any file that needs to match repo style. You do not need to enumerate the conventions explicitly; Claude Code will infer them from examples. Two or three representative files produce better alignment than a written style guide.

In Example 2, Claude Code marked the `password` variable as `sensitive = true` and immediately noted a limitation. What was that limitation?
ASensitive variables cannot have default values in Terraform
BSensitive variables are encrypted at rest in the state file
CMarking a variable sensitive suppresses it from plan output but does not encrypt it in the state file
DSensitive variables require a minimum length validation rule
`sensitive = true` suppresses the variable's value from `terraform plan` and `terraform apply` output — it will not appear in logs. However, the value is still stored in plaintext in the Terraform state file. Engineers who believe `sensitive = true` secures the state backend are mistaken.
