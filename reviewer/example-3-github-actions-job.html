Step 1 of 5
The problem

The payment-api service now has a Dockerfile and a Terraform module. The next step is a CI pipeline that runs on every pull request: install dependencies, run the test suite, build the Docker image, and push to ECR if the branch is main. The pipeline needs to be production-grade from day one because three other teams will be using the same pattern for their own services.

Requirements
— Trigger on push to main and on all pull requests
— Jobs: test (install, lint, unit tests) and build-push (Docker build + ECR push, main branch only)
— Node.js version matrix: test against 18.x and 20.x
— Dependency caching: npm cache keyed on package-lock.json
— AWS auth via OIDC — no long-lived credentials stored as secrets
— ECR region: ap-south-1, image tagged with git SHA
— build-push must only run after test passes on both Node versions
— The workflow must be reusable — callable from other repos via workflow_call

The reusability requirement is what makes this non-trivial. A standard workflow that just runs tests is straightforward. A reusable workflow with OIDC authentication, matrix testing, and conditional ECR push requires understanding several GitHub Actions patterns that interact in non-obvious ways.

Step 2 of 5
The naive approach

Here is the workflow an engineer under time pressure typically writes — referencing a previous project's CI config, adapting it quickly, and calling it done when the first run goes green.

.github/workflows/ci.yml (naive) yaml 
name: CI

on:
  push:
    branches: [ main ]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      # Hardcoded Node version — no matrix
      - uses: actions/checkout@v3
      - uses: actions/setup-node@v3
        with:
          node-version: '18'
      # No caching — full reinstall every run
      - run: npm install
      - run: npm test

  build-push:
    runs-on: ubuntu-latest
    # No dependency on test job — runs in parallel
    steps:
      - uses: actions/checkout@v3
      # Long-lived AWS credentials stored as secrets
      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v2
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ap-south-1
      - name: Login to ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v1
      - name: Build and push
        # Pushes on every branch, not just main
        run: |
          docker build -t ${{ steps.login-ecr.outputs.registry }}/payment-api:${{ github.sha }} .
          docker push ${{ steps.login-ecr.outputs.registry }}/payment-api:${{ github.sha }}

This workflow runs. Tests pass, image gets pushed, the team moves on. But it has six problems that will cost real time and money:

  • Security
    Long-lived AWS credentials stored as repository secrets. AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY are static credentials that never expire. If the repository is compromised, or if the secrets are accidentally logged, those credentials remain valid until manually rotated. OIDC eliminates this entirely — no credentials are stored anywhere.
  • Correctness
    build-push has no dependency on test. Without needs: test, both jobs run in parallel. A broken commit that fails tests will still push a broken image to ECR. Any downstream system that pulls latest or the SHA tag will pick up the broken image.
  • Correctness
    Image is pushed on every branch, not just main. Every PR that touches Docker will push an image to ECR. Over time this floods ECR with images from feature branches that were never merged, bloating storage costs and making it impossible to identify what's actually running in production.
  • Cost
    No dependency caching. npm install downloads all dependencies from scratch on every run. For a large node_modules, this adds 2–4 minutes per run and increases network egress costs. At 50 PRs/week, this is 100–200 minutes of avoidable runtime per week.
  • Coverage
    Tests only run on Node 18. The service targets Node 20 in production. Compatibility regressions between Node versions — particularly around native modules, crypto APIs, and fs behaviour changes — will not be caught until they appear in staging or production.
  • Reusability
    Not reusable across repos. The workflow uses on: push and on: pull_request triggers only. Other teams cannot call it via workflow_call. Each team will copy-paste and diverge, making future security or tooling updates require changes across every repo.
The core problem
The naive workflow optimises for getting the first run green as fast as possible. Production-grade CI optimises for correctness, security, cost efficiency, and maintainability across all future runs. These are different objectives — and the gap between them only becomes visible when something goes wrong.

Turn 1 of 3 — Initial generation
Engineer → Claude Code

Generate a GitHub Actions workflow for the payment-api Node.js service with these requirements:

Triggers: push to main, all pull_requests
Jobs: (1) test — runs on Node 18.x and 20.x matrix, installs with npm ci, runs npm run lint and npm test, npm cache keyed on package-lock.json hash; (2) build-push — Docker build and ECR push, only runs after test matrix passes, only on main branch
AWS auth: OIDC, not long-lived credentials. Role ARN from secret: AWS_ROLE_ARN. Region: ap-south-1
Image tag: git SHA. ECR registry from aws-actions/amazon-ecr-login output

Claude Code
.github/workflows/ci.yml (turn 1 output) 
name: CI

on:
  push:
    branches: [ main ]
  pull_request:

permissions:
  contents: read
  id-token: write   # Required for OIDC token request

jobs:
  test:
    name: Test (Node ${{ matrix.node-version }})
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [ '18.x', '20.x' ]
      fail-fast: false   # Run all matrix versions even if one fails

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Node.js ${{ matrix.node-version }}
        uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'npm'
          cache-dependency-path: package-lock.json

      - name: Install dependencies
        run: npm ci

      - name: Lint
        run: npm run lint

      - name: Test
        run: npm test

  build-push:
    name: Build and push to ECR
    runs-on: ubuntu-latest
    needs: test   # Waits for all matrix jobs to pass
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Configure AWS credentials via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: ap-south-1

      - name: Login to Amazon ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Build and push Docker image
        env:
          REGISTRY: ${{ steps.login-ecr.outputs.registry }}
          IMAGE_TAG: ${{ github.sha }}
        run: |
          docker build -t $REGISTRY/payment-api:$IMAGE_TAG .
          docker push $REGISTRY/payment-api:$IMAGE_TAG
          echo "image=$REGISTRY/payment-api:$IMAGE_TAG" >> $GITHUB_OUTPUT

Key decisions:

— permissions: id-token: write is required at the workflow level for OIDC to work. Without it, the token request to GitHub's OIDC provider will be denied and the AWS credentials step will fail with a cryptic error.

— fail-fast: false on the matrix means both Node versions complete their run even if one fails. This gives you the full picture of which versions are broken, rather than stopping at the first failure.

— needs: test on build-push waits for all matrix jobs — not just one. GitHub Actions treats a matrix job as a single job group; needs will block until every matrix variant has a success status.

— The if condition on build-push uses both github.ref and github.event_name. Using only github.ref would still trigger on pull requests targeting main from a fork, which could push untrusted code to your ECR. The event_name == 'push' check ensures only merged commits trigger the push.

Claude Code

"Resource not accessible by integration" with OIDC credentials is almost always a permissions scope issue at the job level, not the workflow level.

The workflow has permissions: id-token: write set at the top level, but when a permissions block is declared at the workflow level, GitHub Actions scopes it only to jobs that don't declare their own permissions. The build-push job needs its own explicit permissions block:

Fix — add permissions block to build-push job 
  build-push:
    name: Build and push to ECR
    runs-on: ubuntu-latest
    needs: test
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    permissions:               # Add this block
      contents: read
      id-token: write           # OIDC token request

    steps:
      # ... rest unchanged

The root cause: GitHub's default token permissions were tightened in 2023 for security. When any permissions key is present at the workflow level, child jobs that need additional permissions must declare them explicitly — they do not inherit. The test job only needs contents: read (checkout), which is the GitHub default, so it worked without its own block. The build-push job needs id-token: write for OIDC — and without an explicit job-level block, it cannot get it.

This is one of the most common OIDC setup failures and one of the least obvious because the error message points at credentials, not at permissions.

Refactor the workflow to be reusable via workflow_call. Requirements:

— Keep the existing push and pull_request triggers so the workflow still runs standalone in this repo

Claude Code

The key pattern here is using inputs.* with || fallback expressions so the workflow behaves correctly both when called standalone and when called via workflow_call:

.github/workflows/ci.yml (turn 3 — reusable) 
name: CI

on:
  push:
    branches: [ main ]
  pull_request:
  workflow_call:
    inputs:
      ecr-repository:
        description: 'ECR repository name (e.g. payment-api)'
        required: true
        type: string
      aws-region:
        description: 'AWS region for ECR'
        required: false
        type: string
        default: ap-south-1
      node-versions:
        description: 'JSON array of Node.js versions to test against'
        required: false
        type: string
        default: '["18.x","20.x"]'
    secrets:
      aws-role-arn:
        description: 'IAM role ARN to assume via OIDC for ECR push'
        required: true
    outputs:
      image-uri:
        description: 'Full ECR image URI including tag (e.g. 123.dkr.ecr.ap-south-1.amazonaws.com/payment-api:abc1234)'
        value: ${{ jobs.build-push.outputs.image-uri }}

permissions:
  contents: read

jobs:
  test:
    name: Test (Node ${{ matrix.node-version }})
    runs-on: ubuntu-latest
    strategy:
      matrix:
        # fromJSON parses the input string into an array for the matrix
        node-version: ${{ fromJSON(inputs.node-versions || '["18.x","20.x"]') }}
      fail-fast: false

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Node.js ${{ matrix.node-version }}
        uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'npm'
          cache-dependency-path: package-lock.json

      - name: Install dependencies
        run: npm ci

      - name: Lint
        run: npm run lint

      - name: Test
        run: npm test

  build-push:
    name: Build and push to ECR
    runs-on: ubuntu-latest
    needs: test
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    permissions:
      contents: read
      id-token: write
    outputs:
      image-uri: ${{ steps.build.outputs.image }}

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Configure AWS credentials via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.aws-role-arn || secrets.AWS_ROLE_ARN }}
          aws-region: ${{ inputs.aws-region || 'ap-south-1' }}

      - name: Login to Amazon ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Build and push Docker image
        id: build
        env:
          REGISTRY: ${{ steps.login-ecr.outputs.registry }}
          REPO: ${{ inputs.ecr-repository || 'payment-api' }}
          IMAGE_TAG: ${{ github.sha }}
        run: |
          docker build -t $REGISTRY/$REPO:$IMAGE_TAG .
          docker push $REGISTRY/$REPO:$IMAGE_TAG
          echo "image=$REGISTRY/$REPO:$IMAGE_TAG" >> $GITHUB_OUTPUT

The inputs.node-versions || '["18.x","20.x"]' pattern: when run standalone (push/pull_request trigger), inputs.node-versions is undefined, so the || fallback provides the default. When called via workflow_call, inputs.node-versions is populated by the caller. The fromJSON() wrapper converts the JSON string to an array that the matrix strategy can iterate.

Secret resolution: secrets.aws-role-arn || secrets.AWS_ROLE_ARN handles both invocation modes — the kebab-case name is available when called via workflow_call, the UPPER_CASE name is used when run standalone in this repo.

Calling this from another repo:

Caller workflow example (other-service/.github/workflows/ci.yml)
jobs:
  ci:
    uses: your-org/payment-api/.github/workflows/ci.yml@main
    with:
      ecr-repository: other-service
      node-versions: '["20.x"]'
    secrets:
      aws-role-arn: ${{ secrets.AWS_ROLE_ARN }}

  deploy:
    needs: ci
    steps:
      - name: Deploy image
        # Use the output from the reusable workflow
        run: echo "Deploying ${{ needs.ci.outputs.image-uri }}"

The refined output

The Turn 3 output is the final workflow. Here is a diff of what changed from the naive version — every line added is a decision with a reason.

Naive → final: key differences
on: push: ... pull_request: workflow_call: # reusable from other repos inputs: { ecr-repository, aws-region, node-versions } secrets: { aws-role-arn } outputs: { image-uri } permissions: # least-privilege default contents: read jobs: test: # single Node version: '18' strategy: # matrix: 18.x and 20.x matrix: node-version: ${{ fromJSON(inputs.node-versions || '["18.x","20.x"]') }} fail-fast: false - run: npm install # no cache, full reinstall - uses: setup-node@v4 # built-in npm cache with: { cache: 'npm', cache-dependency-path: package-lock.json } - run: npm ci # exact lockfile install build-push: # no needs — runs parallel to test needs: test # blocks until all matrix jobs pass if: github.ref == 'refs/heads/main' && github.event_name == 'push' permissions: # job-level OIDC permission id-token: write aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }} # long-lived aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }} role-to-assume: ${{ secrets.aws-role-arn || secrets.AWS_ROLE_ARN }}
  • Security
    OIDC replaces long-lived credentials. No static AWS keys stored anywhere. The IAM role is assumed via a short-lived token scoped to this workflow run. Rotation is automatic. If the repo is compromised, there are no credentials to extract.
  • Correctness
    needs: test blocks on the full matrix. Both Node 18 and Node 20 must pass before any image is built or pushed. A version-specific regression is caught before it reaches ECR.
  • Cost
    npm cache via setup-node. The cache is keyed on package-lock.json. On a cache hit, npm ci installs from the local cache instead of the registry. For a typical Node service, this saves 2–4 minutes per run across both matrix jobs.
  • Reusability
    workflow_call with typed inputs and outputs. Other repos can consume this workflow without duplicating it. The image-uri output lets caller workflows chain a deploy job without re-deriving the image name.

Watch out

Claude Code handled OIDC setup, matrix strategy, caching, dependency ordering, and the reusable workflow pattern correctly. Here is what it cannot verify or enforce without your specific environment.

What Claude Code handled well
OIDC auth with job-level permissions, fail-fast: false on the matrix, needs blocking on all matrix variants, npm cache via setup-node built-in, dual-mode secret resolution, fromJSON for the matrix input, workflow_call outputs wired through job outputs to workflow outputs. These are non-trivial patterns — the Turn 2 permissions bug diagnosis was particularly accurate.
  • Verify
    IAM role trust policy must include the GitHub OIDC subject. Claude Code cannot see your AWS account. The role's trust policy must allow token.actions.githubusercontent.com as the OIDC provider and must include a sub condition scoped to your repo and branch — otherwise OIDC will fail at runtime with an access denied error that looks identical to a permissions misconfiguration. A trust policy scoped to repo:your-org/payment-api:ref:refs/heads/main is the minimum.
  • Verify
    Cache hits require a prior successful run. On the first run after adding caching, there will be a cache miss and a full install. This is expected. Check the Actions cache tab after the second run — if the cache is not being hit, the cache-dependency-path may not match where your package-lock.json actually lives (monorepo setups often have it in a subdirectory).
  • Verify
    Secret names are case-sensitive and must match exactly. Claude Code generated secrets.aws-role-arn for the workflow_call case and secrets.AWS_ROLE_ARN for the standalone case. If your repo secret is named differently — AWS_ROLE_ARN_PROD, for example — both references fail silently; the credentials step receives an empty value and produces a misleading error. Verify secret names in Settings → Secrets → Actions before the first run.
  • Verify
    workflow_call from a fork requires explicit secret passing. Workflows called from forked repos cannot access the parent repo's secrets by default. If you intend this workflow to be called by external contributors' forks, you need to configure secrets: inherit or pass secrets explicitly in the caller workflow, and enable "Allow GitHub Actions to create and approve pull requests" in org settings. This is a security decision, not a bug.
  • Note
    Action version pinning. The workflow uses @v4 tags, not pinned SHAs. For highest security — particularly in a reusable workflow that other repos will consume — pin to a specific commit SHA (e.g. actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683). This prevents a compromised action from being swapped under a floating tag. Tools like Dependabot and pinact can automate this.
Prompting tip for future pipelines
The most effective addition to Turn 1 was specifying the exact Actions versions (checkout@v4, setup-node@v4, etc.). Without this, Claude Code defaults to whatever version it knows from training — which may be outdated. Always specify action versions explicitly in your prompt. For OIDC specifically, also specify the role ARN source (secret name) and the region — these are the two values most likely to differ between teams and cannot be guessed.
