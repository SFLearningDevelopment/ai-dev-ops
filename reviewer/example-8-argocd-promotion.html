Step 1 of 5
The problem

The team has adopted GitOps: all Kubernetes configuration lives in a Git repository, and Argo CD syncs the cluster state to match. Currently, promotion from staging to prod requires an engineer to manually edit the image tag in the prod manifest, commit, push, and watch the Argo CD UI. This process is error-prone — wrong tag, wrong file, wrong environment — and has no automated health verification before the sync completes.

The task is to build a proper GitOps promotion flow: an ApplicationSet that manages dev, staging, and prod as separate Argo CD Applications, a Kustomize overlay structure that manages image tags per environment, a promotion script that updates the tag via a Git commit rather than a manual edit, and sync policy configurations that are appropriately conservative for prod.

Requirements
— ApplicationSet: single manifest manages dev, staging, prod Applications — each targeting its own overlay directory
— Kustomize overlays: base manifest from Example 7's deployment, per-environment kustomization.yaml with image tag override
— Sync policy: dev auto-syncs; staging auto-syncs with a health check gate; prod requires manual sync, prune and selfHeal explicitly disabled
— Promotion script: updates the image tag in the target environment's kustomization file, commits to Git, and triggers an Argo CD sync — no manual file editing
— Health check: sync waits for the Application to reach Healthy status before reporting success
— targetRevision: pinned to a specific commit SHA for prod, never a branch
Files involved in this example
FilePurposeLayer
argocd/applicationset.yaml ApplicationSet managing all three environment Applications from a single manifest Argo CD
k8s/overlays/dev/kustomization.yaml Dev overlay — image tag override, dev-specific patches Kustomize
k8s/overlays/staging/kustomization.yaml Staging overlay — image tag override, staging-specific patches Kustomize
k8s/overlays/prod/kustomization.yaml Prod overlay — image tag pinned to SHA, prod-specific resource limits Kustomize
scripts/promote.sh Promotion script — updates image tag in Git, commits, triggers Argo CD sync Promotion

Step 2 of 5
The naive approach

The naive GitOps setup has one Argo CD Application per environment, each configured manually, and a "promotion process" that is just an engineer editing a YAML file. It looks like GitOps but retains all the failure modes of manual deployment.

argocd/prod-application.yaml (naive — one Application per env, manually maintained)
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/sourcefuse/payment-api
    targetRevision: main    # Branch — not pinned to a SHA
    path: k8s
  destination:
    server: https://kubernetes.default.svc
    namespace: payment
  syncPolicy:
    automated:
      prune: true    # Deletes resources removed from Git — dangerous in prod
      selfHeal: true # Reverts manual changes — blocks emergency hotfixes

Five failure modes — each one a pattern that is common in early GitOps adoptions:

  • Safety
    targetRevision: main in prod. Prod tracks a branch, not a commit SHA. Any commit pushed to main — including a commit that was intended for dev — is automatically picked up by the prod Application. There is no pinning, no explicit promotion step, and no human decision point between a Git commit and a prod deployment.
  • Safety
    prune: true in prod. If a resource is removed from the Git repository — accidentally deleted, refactored into a different directory, or moved to a different Application — Argo CD will delete it from the cluster. A misconfigured refactor can delete a running Deployment, Service, or PDB without any explicit kubectl delete command.
  • Safety
    selfHeal: true in prod. Any manual change to a Kubernetes resource — an emergency memory limit increase, a temporary replica count adjustment during an incident — will be immediately reverted by Argo CD. This blocks the most common emergency mitigation pattern: a quick kubectl set or kubectl edit to stabilise a service while a proper fix is prepared.
  • Maintainability
    One Application manifest per environment, maintained separately. Three environments means three Application manifests with duplicated configuration. When a field needs to change — the repo URL, the project name, the sync options — it must be changed in three places. An ApplicationSet generates all three from a single template, eliminating the duplication.
  • Correctness
    No Kustomize overlays — all environments share the same manifest. Without overlays, image tag promotion means editing a file that affects all environments simultaneously, or maintaining separate manifest directories that diverge over time. Kustomize overlays let a base manifest be shared while per-environment values (image tag, resource limits, replica count) are applied as targeted patches.
The core problem
The naive setup has the visual structure of GitOps — Git is the source of truth, Argo CD syncs the cluster. But prune: true and selfHeal: true in prod mean that Git has unlimited write authority over the production cluster with no human checkpoint. A wrong commit, a refactored directory, or an accidental file deletion becomes a prod incident. True GitOps for prod requires automation with guardrails, not automation without limits.

Turn 1 of 5 — ApplicationSet with per-environment sync policies
Engineer → Claude Code

Generate an Argo CD ApplicationSet that manages dev, staging, and prod Applications for payment-api. Requirements:

— Repo: https://github.com/sourcefuse/payment-api
— Source path per environment: k8s/overlays/{env}
— Destination namespace: payment for all environments
— Dev: auto-sync, prune true, selfHeal true, targetRevision main
— Staging: auto-sync, prune true, selfHeal false, targetRevision main, health check required before sync complete
— Prod: no auto-sync, prune false, selfHeal false, targetRevision must be injected at sync time (not hardcoded)
— Add retry logic on sync failure: 5 attempts, exponential backoff

Claude Code
argocd/applicationset.yaml (turn 1)
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: payment-api
  namespace: argocd
spec:
  generators:
    - list:
        elements:
          - env: dev
            autoSync: "true"
            prune: "true"
            selfHeal: "true"
            targetRevision: main
          - env: staging
            autoSync: "true"
            prune: "true"
            selfHeal: "false"
            targetRevision: main
          - env: prod
            autoSync: "false"
            prune: "false"
            selfHeal: "false"
            targetRevision: HEAD   # Overridden at sync time by promotion script

  template:
    metadata:
      name: payment-api-{{env}}
    spec:
      project: default
      source:
        repoURL: https://github.com/sourcefuse/payment-api
        targetRevision: "{{targetRevision}}"
        path: k8s/overlays/{{env}}
      destination:
        server: https://kubernetes.default.svc
        namespace: payment

      syncPolicy:
        automated: "{{#if (eq autoSync \"true\")}}"
          prune: "{{prune}}"
          selfHeal: "{{selfHeal}}"
        "{{/if}}"
        syncOptions:
          - CreateNamespace=true
          - ApplyOutOfSyncOnly=true   # Only apply resources that differ — faster syncs
        retry:
          limit: 5
          backoff:
            duration: 5s
            factor: 2
            maxDuration: 3m

      info:
        - name: environment
          value: "{{env}}"

On the conditional automated block: ApplicationSet uses Go templates. The {{#if}} block conditionally includes the automated section only when autoSync is "true". For prod, where autoSync: "false", the automated block is omitted entirely — which is correct: an automated: {} block with no policies still enables auto-sync with defaults in some Argo CD versions.

On ApplyOutOfSyncOnly=true: this sync option tells Argo CD to apply only resources that differ from the cluster state, rather than reapplying all resources on every sync. For a deployment with many resources this significantly reduces sync duration and the number of rolling restarts triggered by syncs.

Turn 3 of 5 — Promotion script
Engineer → Claude Code

Generate scripts/promote.sh. It must:

— Accept: TARGET_ENV (dev/staging/prod), IMAGE_TAG (the SHA tag to promote)
— Update newTag in k8s/overlays/{TARGET_ENV}/kustomization.yaml
— Commit the change with a descriptive message
— Push to the repo
— For prod: also pin the ApplicationSet's targetRevision to the new commit SHA using argocd app set
— Trigger an Argo CD sync and wait for Healthy status (timeout: 5 minutes)
— Exit 0 only if the Application reaches Healthy; exit 1 and print the sync status if it does not
— Requires: argocd CLI authenticated, git, yq for YAML editing

Claude Code
scripts/promote.sh (turn 3)
#!/usr/bin/env bash
# scripts/promote.sh — GitOps image promotion
# Usage: ./promote.sh TARGET_ENV IMAGE_TAG
# Example: ./promote.sh prod abc1234f
# Requires: argocd CLI (authenticated), git, yq v4+
set -euo pipefail

readonly TARGET_ENV="${1:?TARGET_ENV required (dev|staging|prod)}"
readonly IMAGE_TAG="${2:?IMAGE_TAG required}"
readonly APP_NAME="payment-api-${TARGET_ENV}"
readonly KUSTOMIZATION="k8s/overlays/${TARGET_ENV}/kustomization.yaml"
readonly SYNC_TIMEOUT=300

log() { echo "[$(date -u +%H:%M:%S)] $*"; }

# ── Validate environment ───────────────────────────────────────────────────
if [[ ! "$TARGET_ENV" =~ ^(dev|staging|prod)$ ]]; then
  echo "Error: TARGET_ENV must be dev, staging, or prod" >&2
  exit 1
fi

if [[ ! -f "$KUSTOMIZATION" ]]; then
  echo "Error: $KUSTOMIZATION not found — run from repo root" >&2
  exit 1
fi

log "Promoting $IMAGE_TAG to $TARGET_ENV"

# ── Update image tag via yq ────────────────────────────────────────────────
log "Updating $KUSTOMIZATION..."
yq e '.images[0].newTag = "'"$IMAGE_TAG"'"' -i "$KUSTOMIZATION"

# ── Commit and push ────────────────────────────────────────────────────────
git add "$KUSTOMIZATION"
git commit -m "chore(gitops): promote $IMAGE_TAG to $TARGET_ENV

Automated promotion via scripts/promote.sh
Environment: $TARGET_ENV
Image tag:   $IMAGE_TAG
Triggered by: ${GITHUB_ACTOR:-$(git config user.name)}"

log "Pushing to remote..."
git push origin HEAD

# ── Prod: pin targetRevision to the new commit SHA ────────────────────────
if [[ "$TARGET_ENV" == "prod" ]]; then
  COMMIT_SHA=$(git rev-parse HEAD)
  log "Pinning prod targetRevision to $COMMIT_SHA"
  argocd app set "$APP_NAME" --revision "$COMMIT_SHA"
fi

# ── Trigger sync ───────────────────────────────────────────────────────────
log "Triggering Argo CD sync for $APP_NAME..."
argocd app sync "$APP_NAME" --async

# ── Wait for Healthy status ────────────────────────────────────────────────
log "Waiting for $APP_NAME to reach Healthy status (timeout: ${SYNC_TIMEOUT}s)..."
if argocd app wait "$APP_NAME" \
    --health \
    --timeout "$SYNC_TIMEOUT"; then
  log "SUCCESS — $APP_NAME is Healthy after promotion to $TARGET_ENV"
  exit 0
else
  log "FAILED — $APP_NAME did not reach Healthy within ${SYNC_TIMEOUT}s" >&2
  log "Current status:" >&2
  argocd app get "$APP_NAME" --output json | \
    jq '.status | {health: .health.status, sync: .sync.status, conditions: .conditions}' >&2
  exit 1
fi

The prod-specific argocd app set --revision COMMIT_SHA step is the enforcement mechanism that closes the loop: after committing the image tag change, the exact commit SHA is pinned as the prod Application's targetRevision. Any subsequent commits to main will not affect prod — it will only sync to this exact SHA until the promotion script runs again.

kubectl get hpa -n payment returns No resources found — the HPA was not applied.

Claude Code

Two separate issues visible in the status output:

Issue 1 — HPA API version not supported: the error error converting unsupported type "autoscaling/v2/HorizontalPodAutoscaler" means the staging cluster's Kubernetes version does not support autoscaling/v2. This API was promoted to stable in Kubernetes 1.26. Check the cluster version:

Check cluster version
kubectl version --short
# If server version < 1.26, autoscaling/v2 is not available
# Downgrade the HPA manifest to autoscaling/v2beta2 for k8s 1.23–1.25

If the staging cluster is on Kubernetes < 1.26, update k8s/hpa.yaml:

k8s/hpa.yaml — API version downgrade if cluster < 1.26
# Change:
apiVersion: autoscaling/v2
# To:
apiVersion: autoscaling/v2beta2
# Note: v2beta2 supports the same CPU and memory metrics as v2
# but was only available as beta in Kubernetes 1.23–1.25

Issue 2 — Degraded health is a consequence: the HPA not being applied means the Deployment has no autoscaler. The Minimum number of live pods not available message means the Deployment cannot reach its desired replica count — likely because the HPA would normally adjust the replica count and it is absent. Once the HPA API version is corrected and the HPA is applied, the Deployment health should recover. The two issues are connected.

The prod cluster version should be verified before the prod promotion — prod may be on the same version as staging, in which case the same fix is needed there.

The refined output

Five files implementing a complete GitOps promotion flow. The diff below shows the key changes from the naive Application manifest, and the connection diagram maps how the files coordinate.

Naive Application → refined ApplicationSet: key differences
kind: Application # One per env — three separate files kind: ApplicationSet # One file generates all three Applications targetRevision: main # Branch — any push promotes to prod targetRevision: "{{targetRevision}}" # Per-env: main for dev/staging, SHA for prod automated: prune: true # Deletes resources removed from Git selfHeal: true # Reverts manual emergency changes automated: # Dev only — staging/prod omit or restrict prune: "{{prune}}" # Controlled per environment selfHeal: "{{selfHeal}}" # Prod: false — manual changes permitted syncOptions: - ApplyOutOfSyncOnly=true # Only apply changed resources retry: # 5 attempts, exponential backoff limit: 5 backoff: { duration: 5s, factor: 2, maxDuration: 3m }
How the five files coordinate
argocd/applicationset.yaml →
Generates three Argo CD Applications from a single template. Each Application targets its environment's overlay directory (k8s/overlays/{env}) and has its own sync policy. The ApplicationSet controller watches this file — any change to the template propagates to all three Applications.
k8s/overlays/{env}/kustomization.yaml →
The promotion target — the only file the promotion script modifies. The images[0].newTag field is the single source of truth for which image is running in each environment. Argo CD reads this file on each sync cycle; changing the tag triggers a diff and initiates a rollout. The prod overlay additionally applies the memory limit patch.
k8s/ (base manifests) →
Referenced by all three overlays via resources: ../../. The base deployment, HPA, PDB, and service manifests are shared across all environments. Environment differences are applied as overlays, not as separate copies of the base files. This prevents base manifest changes from requiring updates in three places.
scripts/promote.sh →
Orchestrates the promotion: Git commit → Argo CD sync → health check. The script is the human-triggerable automation that replaces manual file editing. For prod, it additionally pins the ApplicationSet's targetRevision to the exact commit SHA, closing the branch-tracking gap in the naive approach.

Watch out

Claude Code produced a correct GitOps promotion structure with appropriate per-environment sync policies. Here is what requires cluster-specific verification.

What Claude Code handled well
Per-environment sync policy differences expressed correctly in a single ApplicationSet template, prune: false and selfHeal: false for prod with clear reasoning, PLACEHOLDER tag as an intentional fail-safe in the prod overlay, argocd app set --revision COMMIT_SHA to pin prod after promotion, two-issue diagnosis in Turn 4 (HPA API version incompatibility causing Deployment health degradation), ApplyOutOfSyncOnly=true sync option included without prompting, overlay audit correctly flagging the REGISTRY placeholder as the one deployment prerequisite.
  • Verify
    The ApplicationSet conditional template syntax requires Argo CD ≥ 2.6. The {{#if (eq autoSync "true")}} Go template syntax for conditionally including the automated block requires Argo CD 2.6 or later. Earlier versions do not support conditional blocks in ApplicationSet templates. Check your Argo CD version with argocd version and verify the template syntax matches your version's supported features.
  • Verify
    The promotion script requires the argocd CLI to be authenticated. argocd app sync and argocd app wait require an active argocd CLI session. In CI, this means authenticating with a service account token before the promotion script runs: argocd login --auth-token $ARGOCD_TOKEN. The script does not handle authentication — it assumes the CLI is pre-authenticated in the environment that calls it.
  • Verify
    Replace the REGISTRY placeholder in all four locations before the first promotion. The image name REGISTRY/payment-api appears in k8s/deployment.yaml and all three overlay kustomization.yaml files. Kustomize matches image names exactly — if the name in the overlay does not exactly match the name in the deployment manifest (including the registry prefix), the tag override is silently skipped and the base image runs instead. Verify with kustomize build k8s/overlays/prod | grep image: after substituting the real registry.
  • Verify
    The yq command targets images[0].newTag — verify index. The promotion script uses yq e '.images[0].newTag = "..."'. This updates the first image in the images array. If any overlay ever adds a second image (e.g. an init container or sidecar image), the index may need to change. Use a more specific selector in production: yq e '(.images[] | select(.name == "REGISTRY/payment-api")).newTag = "..."' to target by name rather than index.
  • Note
    The prod commit SHA pinning survives only until the next ApplicationSet reconciliation. When argocd app set --revision COMMIT_SHA pins the prod Application's revision, it modifies the live Application object in the cluster. If the ApplicationSet reconciles (due to a change to the ApplicationSet manifest itself), the targetRevision field will be reset to the value in the template — which is HEAD. For durable SHA pinning, the SHA should be written back into the ApplicationSet template itself or managed via a dedicated prod Application manifest outside the ApplicationSet.
Prompting tip for GitOps configuration
The most important framing for any Argo CD or GitOps prompt is stating the sync policy intent explicitly for each environment — not just "auto-sync for dev, manual for prod." The specific flags matter: prune, selfHeal, and targetRevision each have non-obvious production implications that Claude Code will get right when told the intent (e.g. "selfHeal false so manual emergency changes are not reverted") but may default incorrectly when told only the outcome (e.g. "conservative sync for prod"). Name the operational risk you are guarding against for each flag, not just the desired setting.
